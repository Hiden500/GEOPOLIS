Дата: 2026-07-10. Проведён как Фаза 1 протокола `.claude/agents/ui-designer.md`
(независимый анализ без правок кода, по прямому запросу пользователя —
текущий дизайн признан неподходящим). Мандат: современные методы фронтенд-
разработки + user-friendly интерфейс (понятный, легкоусваиваемый,
неперегруженный) для игрока, который не обязан быть ветераном Paradox-жанра.

Метод: сплошной обход `client/src/components/**`, `App.css`, `useWindows.ts`,
разбор реального игрового потока (ScenarioSelector → GameView → окна →
LLM-цикл). Находки ранжированы по тому, что реально мешает игроку, не по
вкусовым придиркам. Это отчёт, не план реализации — реализация ждёт вашего
направления (см. «Направления» в конце).

## Находки высокой серьёзности

### 1. Основной игровой цикл требует ручного copy-paste во внешний сайт

`LLMPanel.tsx` — цикл хода по умолчанию: нажать «получить промт» → промт
копируется в буфер → игрок сам открывает внешнюю LLM, вставляет, копирует
ответ → вставляет обратно в textarea → «применить». Есть автоматический путь
(`handleAuto`), но он требует `GEMINI_API_KEY` в `server/.env`, и если ключ не
настроен — интерфейс никак это не объясняет, просто вернёт ошибку
(`t("errors.autoCycle")`). Это самый частый и самый важный экран во всей
игре, и по умолчанию он выглядит и работает как инструмент разработчика, не
как ход в игре. Для игрока, ожидающего игровой опыт (а не встроенный DevTools
для промт-инжиниринга), это стена сразу на первом ходу.

### 2. Числа форматируются по хардкод-локали независимо от языка интерфейса

`InspectorPanel.tsx:43,48,110`, `BudgetPanel.tsx` (5+ мест) —
`.toLocaleString("ru-RU")` зашито буквально, не зависит от выбранного
языка. Игрок, выбравший English на старте (`ScenarioSelector.tsx`), всё равно
увидит числа в русском формате (пробел как разделитель тысяч и т.п.). Это не
косметика — это прямое нарушение уже принятого в проекте принципа
мультиязычности (`docs/LOCALIZATION.md`), реализованное с ошибкой.

### 3. Несколько окон одного типа схлопываются в одну позицию

`useWindows.ts:41-45` (`getSettingsKey`) сохраняет позицию окна по
**категории** (`"country"`, `"region"`), не по конкретному экземпляру. Сценарий
из `docs/decisions/2026-06.md` («сравнить две страны рядом») ломается на
практике: подвинули окно первой страны → у настройки в localStorage теперь
есть сохранённая позиция для ключа `"country"` → второе открытое окно другой
страны стартует **в той же точке**, а не со смещением, и визуально ложится
поверх первого. Заявленная фича не работает так, как задумана.

### 4. Верхняя панель статов нечитаема для нового игрока

`TopStatBar.tsx` — шесть чисел (`2.34T`, `1.2M`, `62`, `58%`...) без единиц,
без шкалы, без объяснения «это хорошо или плохо». Ветеран Paradox-игр
интерпретирует это интуитивно по жанровой конвенции; игрок без этого опыта —
нет. Ни tooltip, ни легенды, ни цветового кодирования «в норме/тревога»
(кроме status-stamp по одному признаку — войны/соперники) нет нигде.

### 5. Сырые данные без перевода и единиц измерения

`InspectorPanel.tsx:140` — производство ресурсов региона выводится как
`{resource}` (буквальный id: `iron`, `coal`, `food`) без локализации даже на
русский, без иконки, без единицы измерения. Технологии показаны только
числом («Освоенных доменов: 3») без названий доменов. Игрок не может понять,
чем богат регион или в чём страна технологически развита, не читая исходный
код.

### 6. Нет онбординга — жёсткий обрыв в плотный HUD

Переход ScenarioSelector → GameView — это прыжок из простого выбора в экран с
шапкой из 6 чисел, 5 кнопок навигации, картой, тикером ресурсов и системой из
9 типов плавающих окон — без единой подсказки, что это, зачем и с чего
начать. Ни одно из полей (`docs/plans/09_MECHANICS_BACKLOG.md`, п. 4.3
касается автоматизации, но не онбординга) не покрывает первые 5 минут игрока.

### 7. У оконной системы нет управления на масштабе

9 типов окон + потенциально много одновременных country/region-инспекторов —
и ни одной операции уровня «сбросить раскладку», «закрыть все», «свернуть».
При заявленной цели поддерживать «сотни стран» (docs/PROJECT.md) и
любопытство игрока, открывающего много окон подряд, отсутствие управления
раскладкой — не мелочь, а ограничение, которое будет только хуже с ростом
контента.

### 8. Свободный текст намерения — чёрный ящик без границ

`PlayerIntentPanel.tsx` — автокомплит есть только для упоминания регионов
(`@`), но нет ни одной подсказки о том, какие вообще действия LLM способна
понять и исполнить (типы действий из `LLMResponseValidator` игроку не видны).
Игрок пишет в пустоту, не зная границ возможного — узнаёт о лимитах только
постфактум, из списка отклонённых действий после хода.

## Находки средней серьёзности

### 9. Один файл CSS на 1600+ строк без изоляции

`App.css` — плоский набор глобальных классов без CSS Modules/scoping. Каждая
новая панель добавляет N новых глобальных имён без защиты от коллизий; при
9 панелях файл уже перевалил за 1600 строк. Это прямо то, что просил
пересмотреть запрос «современные методы разработки» — не вопрос вкуса.

### 10. Нет переиспользуемых примитивов — только похожие ad-hoc паттерны

Три независимых варианта «чипа» (`.stat-pill`, `.resource-chip`,
`.timeline-tag`) с разной разметкой, решающие одну задачу — компактно
показать значение с подписью. Нет общего `<Stat>`/`<Chip>`/`<Button>`
компонента. Нет каталога компонентов (Storybook или аналог) — оценить полный
набор состояний экрана можно только вручную открыв игру.

### 11. Доступность не проработана

Ни одного явного `:focus-visible` правила в App.css — клавиатурная навигация
на кастомной тёмной теме в лучшем случае полагается на браузерный дефолт.
Непоследовательно: `ScenarioSelector` использует `aria-pressed` на переключателях
верно, `header-nav` кнопки в `TopStatBar.tsx` — нет (только CSS-класс `active`).
Иконка-кнопка закрытия окна имеет `aria-label`, но не единственная в своём роде
проверка — полного прохода по WCAG не делалось.

### 12. Десктоп-only допущение в игровом экране

Адаптивность есть только в `ScenarioSelector` (скролл, `max-height`). Сама
`GameView`/оконная система рассчитана на большой десктопный вьюпорт; `Window.tsx`
ограничивает позицию, но не решает случай, когда несколько окон физически не
помещаются на маленьком экране одновременно.

### 13. Сырые сообщения об ошибках долетают до игрока

Несколько обработчиков в `GameView.tsx` и `LLMPanel.tsx` показывают
`err.message` напрямую — если сервер вернёт техническое исключение, игрок
увидит его как есть, без перевода в понятную формулировку.

## Находки низкой серьёзности

### 14. Мёртвый шаблонный вес
`client/src/index.css` и `client/public/icons.svg` — остатки create-vite
шаблона (светлая/тёмная докс-тема, иконки bluesky/discord/github), к игре
отношения не имеют. Не критично, но лишний вес и потенциальный источник
путаницы при будущих правках.

### 15. Равномерно высокая плотность без иерархии
Размеры текста почти везде в диапазоне 0.6–0.9rem, моно-шрифт доминирует.
Последовательно, но не даёт глазу «главного» — нет визуального уровня
«это самое важное сейчас» отдельно от «это деталь». Прямая причина ощущения
перегруженности, о которой говорит запрос.

## Итог: что это значит вместе

Находки 1, 4, 5, 6, 8 — это одна и та же проблема с разных сторон: **интерфейс
спроектирован для игрока, который уже знает жанр и в идеале не против
поработать руками с внешней LLM.** Это конфликтует напрямую с целью
«user-friendly, понятный, легкоусваиваемый». Находки 2, 3, 13 — это не дизайн,
а баги в уже принятых решениях (мультиязычность, сравнение окон, обработка
ошибок) — их стоит чинить независимо от того, какое направление вы выберете
дальше. Находки 9–11 — это ровно то, что просил пересмотреть запрос
«современные методы разработки»: они не видны игроку напрямую, но определяют,
насколько дёшево дальше чинить находки 1–8 и добавлять новое, не ломая старое.

## Направления (выбор — за вами; ниже моя рекомендация)

Направления не взаимоисключающие — это оси решения, не пакеты «всё или ничего».

**A. Guided HUD** — не переизобретать визуальный язык, а исправить
информационную архитектуру: онбординг первого хода, объяснение чисел
(единицы/легенда/tooltip), прогрессивное раскрытие сложности (сначала простой
вид, детали — по запросу), управление раскладкой окон, понятные подсказки для
намерения игрока. Наименьшие риск и объём работы, самый прямой удар по целям
«понятный, легкоусваиваемый».

**B. Современный фронтенд-фундамент** — CSS Modules/токены как код (не только
как документ), общий набор примитивов (Stat/Chip/Button/Card), устранение
локаль-бага и сырых ошибок. Не видно игроку напрямую как «редизайн», но это
именно ответ на «современные методы разработки» и то, что делает A и любое
дальнейшее развитие дешевле, а не дороже со временем.

**C. Полный визуальный и IA-редизайн** — пересмотр самой эстетики
«штабной сводки»: возможно, она сама по себе (плотная, военно-канцелярская,
моно-тяжёлая) — часть проблемы «перегруженности», не только реализация.
Наибольший риск и объём, но и наибольший потолок для «user-friendly», если
проблема не только в отсутствии онбординга, а в самом визуальном языке.

**Моя рекомендация:** B и A вместе, в этом порядке приоритета внутри — B
даёт фундамент, на котором A реализуется быстро и не оставляет технического
долга; C оставить открытым вопросом до тех пор, пока вы не поживёте с
улучшенной IA (A) и не увидите, ощущается ли сама эстетика проблемой отдельно
от беспорядка вокруг неё, или беспорядок и был всей проблемой. Обе — 2 и 3
(локаль-баг, схлопывание окон) — чинить независимо от выбора направления,
это не дизайн-решение, а исправление уже сломанного.

Скажите, какое направление (или комбинацию) брать в работу — агент переходит
в Фазу 2 только после этого.
