## 2026-07-04 (пользователь) — Действия игрока свободным текстом вместо структурной ActionPanel

Решение: `ActionPanel`/`PlayerActionService` (сейчас декоративны — `createAction` пишет в массив, ни один тик не читает, единственный потребитель — текст в LLM-промте) заменяются на свободный текстовый ввод намерения игрока (с подсказками по `regionId`/типам — автокомплит, не жёсткий dropdown). Намерение уходит в тот же ежемесячный LLM-промт, LLM интерпретирует его в `LLMAction[]` (тот же тип, что уже применяет `processResponse`) — числа считает движок, LLM решает "что". Обсуждались два варианта (расширить структурную форму vs свободный текст) — выбран свободный текст.

Причина: реальный референс проекта — коммерческая игра Pax Historia (paxhistoria.co) с моделью "words → action → reaction" (игрок пишет намерение словами, ИИ решает реакцию) — структурная форма с 4 хардкоженными типами действий (`build_factory`/`build_mine`/...) расходится с этим духом и всё равно не работает (декоративна). Свободный текст через уже существующий LLM-цикл не требует нового пайплайна — переиспользует то, что уже построено для мировых событий.

Статус: **реализовано (2026-07-05)**. `ActionPanel`/`PlayerActionService`/`PlayerAction` удалены целиком (включая мёртвый `BuildSimulationPrompt.ts` — тот же обречённый паттерн). `GameState.playerIntent: string` — одноразовое поле на текущий ход, не история (полноценная "память страны между ходами" — отдельная, сознательно отложенная задача, см. `docs/TODO.md` P2.5); очищается в `LLMService.processResponse` после успешного применения ответа. Промт получил секцию `## Player Intent`. Клиент: новая `PlayerIntentPanel` (окно "Намерение") — textarea с лёгким кастомным автокомплитом по своим регионам (триггер `@`, вставляет `id: Название`) вместо структурных dropdown'ов. regionId-grounding решён на входе (игрок выбирает регион из автокомплита и получает реальный id прямо в тексте) — отдельная секция `## Your Regions` в промте сознательно не добавлена: `LLMAction` всё равно не читает regionId из ответа LLM, а для стран с сотнями регионов такая секция раздувала бы промт без пользы. tsc/тесты зелёные.

## 2026-07-04 (Claude) — Перезаполнение экономики регионов 1946 (методология, исключающая прошлую ошибку)

Решение: по итогам аудита (запись ниже) пользователь выбрал "переделать с более строгой методологией". Ключевая находка при разборе кода, изменившая объём работы: `region.gdp` из JSON **не используется как есть** — `initializeRegionGdp()` (`shared/src/utils/aggregateCountryData.ts`) безусловно перезаписывает его формулой `population × development × infrastructure × 1000` при каждом `createGame()`. Значит не нужно источниковать абсолютные ВВП в долларах (слабое место прошлой попытки) — реально важны только `population` (единственное поле, суммируемое в страну без трансформации) и реалистичные **относительные** `development`/`infrastructure` (0..1).

Новые скрипты (`scripts/map/economy_1946/` + `fill_region_economy_1946.py` + `validate_region_economy_1946.py`):
1. **Якоря населения** (`anchors.py`) — 127 стран, каждый с confidence (`verified`/`estimated`) и source note. Китай — **один** исторический тотал (~490М, League of Nations-era оценка), делится между `CHN`/`TWN`/`QMS` по реальной пропорции гражданской войны (Гоминьдан ~350М материка, коммунистические базовые районы ~110М, советская Маньчжурия ~30М) — структурно исключает прошлое задвоение. Германия (4 зоны) и Британская Индия — реальные цифры, подтверждённые WebSearch в этой сессии.
2. **Распределение внутри страны** (`density_tiers.py`) — вес региона = `area^0.55 × TIER_MULTIPLIER[тир]`, где тир — качественная реальная географическая классификация (явная для стран первого эшелона: СССР/США/Британия/Франция/Италия/Япония/Бразилия/Канада/фрагменты Китая/зоны Германии/Кореи — 46 стран, 77% регионов; generic по квантилям площади для остальных). Степень <1 у площади структурно не даёт огромным пустым территориям (Якутия, Сахара) абсурдную долю просто за размер — в отличие от прошлой линейной density×area.
3. **США — точный оверрайд** (`usa_states.py`) — реальные веса переписи 1940 по штатам вместо tier×area эвристики (самый заметный кейс аудита). Результат: Монтана 596,575 (реально ~559,456, +7%) против прошлых 5.35М (×9.5); Невада 117,562 (реально ~110,247, +7%) против прошлых 4.03М (×25); Вайоминг 267,378 (реально ~250,742, +7%).
4. **Ресурсы** (`resource_geography.py`) — курируемые реальные месторождения (Баку/Донбасс/Урал для СССР, Рур/Саар для Германии, Малайя/Ост-Индия — каучук/олово, Ближний Восток — нефть, Чили — медь/нитраты, ЮАР — золото), только `eraIntroduced <= 1946`.
5. **Валидатор** (`validate_region_economy_1946.py`) — автоматизирует ровно то, что проваливало прошлую попытку: 3+ региона страны с идентичной плотностью (0 нарушений), население/gdp/0..1-поля вне диапазона (0), страновые тоталы vs якоря (допуск 3%, 0 нарушений), Китай не задвоен (490,000,001 vs 490,000,000 тотал), мировой тотал в диапазоне 2.2-2.6 млрд (2,252,044,726), date-gate ресурсов (0 нарушений). **Проходит чисто.**

Живой прогон (`preview_start`, сценарий 1946, USA): ВВП 0.12T / население 141.0M в `TopStatBar` вместо `$0.00B`. LLM-промт (`## Major Powers`) показывает реальные ВВП по всем крупным державам (USA $117.98B, SUN $64.69B, JPN $60.55B, GBR $28.70B, ...) — устраняет ранее наблюдённый гэп.

Не в мандате этой задачи (отдельные, уже существовавшие пробелы, не тронуты): `military.manpower`/`politics.stability`/`politics.legitimacy` — не заполняются заполнением регионов (другие поля, другой уровень модели), остаются на значениях сценария.

Статус: выполнено. tsc/тесты (сервер 258/258, клиент 83/83) зелёные, валидатор чист, живой прогон подтверждён.

## 2026-07-04 (Claude) — Аудит: заполнение экономики регионов 1946 (Gemini) не влито и содержит серьёзные ошибки

Решение: по запросу пользователя проверена достоверность заполнения экономики регионов 1946 (запись выше, 2026-07-03). Два независимых, каждое из них достаточное само по себе, отдельных вывода:

1. **Не влито в `main`.** Работа сделана на ветке `gemini/map-data-filling` (коммит `03bfda3`), которая разошлась с `main` сразу после `2c35941` и никогда не мержилась. Живой `main` до сих пор держит все 1366 регионов на нулевых плейсхолдерах (`population=0`, `gdp=0`) — этим объясняется наблюдённый ранее `$0.00B` у СССР в промте LLM (записано в `docs/TODO.md` как общий гэп, теперь известна точная причина).
2. **Содержимое самой ветки, если бы её влить, недостоверно.** Проверка агрегатов по странам (сравнение с историческими цифрами 1946): население/ВВП по большинству крупных стран (`USA` 141.9M, `GBR` 49.2M, `FRA` 40.3M, `ITA` 45.7M, `BRA` 47.3M — все близко к реальным цифрам) выглядят правдоподобно на уровне страны. Но:
   - **Китай задвоен.** `CHN` (520M) + `TWN` (450M) + `QMS` (40M) = **~1.01 млрд** — вдвое больше реального населения Китая в 1946 (~490-520M по Maddison). Похоже, каждому фрагменту независимо присвоили полный страновой тотал вместо разделения одного тотала на три части.
   - **Системный артефакт density×area внутри почти каждой страны.** В большинстве стран (проверено: `USA`, `GBR`, `FRA`, `SUN`, `JPN`, `TWN`, `QCG` и десятки других) 3-4 региона делят ИДЕНТИЧНУЮ плотность населения (совпадает до десятичного знака) — не историческая оценка по региону, а механическое умножение площади на одну из нескольких констант-плотностей на страну. Конкретные абсурдные следствия: Монтана (USA) — 5.35M человек (реально ~560K, ×9.5), Невада — 4.03M (реально ~160K, ×25), Ханькоу/совр. Ухань (TWN) — 23.6M (реально для 1946 ~1-1.5M, ×~18), Нагасаки (JPN) — 15.1M (реально ~1.2-1.5M, ×~10) — похоже на путаницу исторических и современных цифр по известным городам. Крупные американские города (Калифорния/Нью-Йорк) занижены компенсаторно — общий тотал страны совпадает с историей, внутреннее распределение — нет.
   - **Мировой тотал населения — 2.83 млрд** против исторических ~2.3-2.4 млрд (+~18-20%, большая часть — из-за Китая).
   - **2 нарушения date-gate ресурсов**: `rareEarths` (eraIntroduced 1980) в Kosovo (`YUG`, регион 365) и Hunan (`TWN`, регион 390) — прямое нарушение требования из `docs/tasks/REGION_ECONOMY_FILL.md`.

Причина: методология (правильные страновые тоталы из Maddison + LLM-субагенты распределяют по регионам) была здравой на бумаге, но проверка на местах показывает, что распределение внутри страны — не историческое исследование, а грубая категоризация "по 2-4 уровня плотности на батч", плюс минимум одна прямая двойная выдача тотала (Китай). Инцидент того же типа, что предупреждает `AGENTS.md`: "Выполнено" ≠ "проверено end-to-end".

Статус: аудит завершён, фикс не сделан в этом проходе (пользователь просил проверку, не исправление). Решение по следующему шагу — за пользователем. Ветка `gemini/map-data-filling` не удалена и не мержится — ждёт решения.

## 2026-07-04 (Claude) — Ротация "Spotlight Countries" (закрыт вопрос 11)

Решение: расширение круга стран, реально ощущающих LLM, реализовано через
ротацию, а не через контент. `LLMService.getMajorPowers()` переписан с
ad-hoc top-5-по-ВВП на `country.tier === 'major'` — поле уже существовало
(`TierTick.ts`, пересчитывается раз в год по составному скору ВВП/военной/
влияния) и просто не было подключено к промту. Остальные (`regional`/
`minor`, ~117 из 127 стран) попадают в новую секцию промта `## Spotlight
Countries` через детерминированный round-robin: пул отсортирован по `id`
(не по ВВП/скору — те меняются каждый тик и сдвигали бы порядок
непредсказуемо), `LLM_SPOTLIGHT_COUNT = 5` стран за цикл, курсор —
`game.llmSpotlightCursor`, двигается только при успешном `processResponse`
(не при `generatePrompt` — генерация промта идемпотентна). При 117 странах и
шаге 5 полный оборот — ~24 месяца игрового времени.

Отклонённая альтернатива: реактивные триггеры (страна попадает в промт при
пересечении дипломатического порога — стала рival/allies, санкция и т.п.)
вместо/вместе с ротацией. Не реализовано в этом проходе — требует снимка
состояния на момент прошлого цикла для детектирования дельты (тик LLM
нерегулярный/ручной, в отличие от помесячных тиков), заметно дороже по
сложности при неочевидном выигрыше сверх простой ротации. Зафиксировано как
возможное будущее расширение, не блокер.

Черновик исторических развилок (`docs/tasks/HISTORICAL_HINGE_POINTS_1946.md`,
см. запись ниже) — отдельный, дополняющий механизм: событийный, не
периодический, и не покрывает все 92 minor-страны (нет смысла авторить
контент на каждую) — ротация и развилки решают разные грани одного вопроса,
не заменяют друг друга.

Статус: выполнено. +6 тестов (сервер 258), tsc чисто на обеих сторонах.

## 2026-07-04 (Claude) — Бюджет игрока переведён на доли income + пресеты + сохранение отдельно от хода

Решение (4 связанных шага, по решению пользователя от предыдущего разбора ECONOMY.md/BudgetPanel):
1. **Серверная валидация** — `updateBudgetSchema` раньше не защищала ничего реально (`.refine(sum≥0)` избыточен, per-category потолки жили только в атрибуте `max` слайдера, прямой `PUT /budget` их игнорировал). Добавлен `.finite()`.
2. **Доли вместо абсолютных денег** — бюджет игрока переведён на ту же модель, что уже использует `EconomyProfile.spending` при создании стран (`docs/ECONOMY.md` "Модель единиц"): `EconomyState.spendingShares` (опционально, ИИ-страны не имеют), потолки в `shared/src/constants/budgetSpendingShareCaps.ts` (единый источник для схемы и клиента), `EconomyTick` пересчитывает `*Spending = income × доля` каждый тик (тот же паттерн, что `taxRate → taxRevenue`) — расходы автомасштабируются с экономикой без повторной правки слайдеров. Шаг 1 (`CountryService.validateBudgetUpdate`) стал не нужен и удалён — его роль полностью взяли статические потолки схемы.
3. **Пресеты** — 4 курируемых набора долей (Военная экономика/Социальное государство/Индустриализация/Аустерити) в `budgetPresets.ts`, кнопки заполняют слайдеры.
4. **Сохранение отдельно от хода** — `GameView.handleUpdateBudget` больше не вызывает `nextTurn()` после сохранения бюджета (только `getGameState()`); `research`/`actions`-хендлеры не тронуты (вне запроса).

Причина: бюджет был спредшит-моделью, которую сам `AGENTS.md` запрещает (Victoria-сложность), без реальной серверной защиты, без связи с уже существующей моделью долей, с обязательным продвижением хода на любую правку.

Статус: выполнено (сервер 252/252, клиент 83/83, tsc чисто на обоих шагах со 2 по 4; живая браузерная проверка не выполнена — Chrome MCP был недоступен в сессии).

## 2026-07-04 (Claude) — Промт даёт LLM реальные country id вместо угадывания по имени

Решение: `generatePrompt` до фикса называл страны только по имени (`c.name`) — LLM была вынуждена придумывать код из имени. ## 2026-07-03 (Gemini) — Коррекция вертикальных/диагональных подписей (Canada/Chile), нормализация вращения букв и масштабирования шрифта

Решение:
1. **2D-валидация направления baseline:** Изменен алгоритм направления в `GeometryEngine.ts`. Вместо горизонтальной проверки `line[last][0] < line[0][0]` внедрена полная проверка по осям X и Y. Если baseline преимущественно вертикальный (`|dy| > |dx|`), он разворачивается при `dy > 0` (что заставляет его течь с юга на север). Это исправило зеркальный и перевернутый вид вертикальных подписей (Canada, Chile), сделав их читаемыми снизу вверх.
2. **Относительная нормализация вращения букв:** Посимвольный переворот углов на границах ±90° заменен на нормализацию относительно глобального угла всей baseline (`globalAngle`). Каждый символ теперь удерживает угол поворота в пределах ±90° от общего вектора направления baseline, исключая скачки вращения и переворот отдельных букв внутри одного слова.
3. **Согласование масштабирования шрифта:** Формула интерполяции `text-size` в `MapView.tsx` заменена на экспоненциальное масштабирование `min(sizeZ7, sizeZ2 * 2^(zoom - 2))`. Это синхронизировало визуальное расстояние между точками-буквами и размер самого шрифта при приближении/отдалении, решив проблему чрезмерной растянутости «Soviet Union» при зуме и слипания мелких надписей в Европе.

Причина: Устранение критических визуальных дефектов (Canada перевернута вверх ногами, буквы Soviet Union разлетаются при зуме, слипание букв в Европе).

Статус: Выполнено. Все 83 клиентских теста и 224 серверных теста успешно проходят, TypeScript компилируется с 0 ошибок.
