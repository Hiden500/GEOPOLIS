## Протокол старта сессии

1. `git checkout main && git pull`; `git log --oneline -10` — что изменилось.
2. `git status` — нет ли незакоммиченного хвоста прошлой сессии. Есть →
   разобраться с ним ПРЕЖДЕ новой работы (докоммитить или доложить).
3. Прочитать: `docs/plans/README.md` (статусы), `docs/TODO.md`,
   `docs/DECISIONS.md` (записи новее последней известной).
4. Выбрать задачу (приоритет: явная задача пользователя → следующий план по
   порядку → TODO).
5. Создать ветку `claude/<task>`.
6. Пройти «Анализ перед изменением» (ниже) для затрагиваемой зоны.

## Протокол анализа перед изменением

Выполняется до первой правки, результат — короткая секция «Анализ» в ответе.

1. **Карта затрагиваемого:** какие файлы/типы/тики/роуты трогает задача.
   Для механик всегда проверять пятёрку: shared-типы → тик/команда → LLM-промт
   и схемы → клиентское отображение → данные сценария.
2. **Существующее:** есть ли уже похожая реализация/утилита/паттерн?
   (grep + `shared/src/utils/`, services). Переиспользуй; параллельная
   реализация — дефект.
3. **Порядок фаз:** если меняется тик — где он в `simulateMonth`, кто читает
   его результат в этом же тике, какие лаги задокументированы.
4. **Контракты:** сериализация (правило 1 конституции), LLM-схемы (правило 6),
   локализация (правило 8), данные (валидации плана 05).
5. **Риски:** что сломается первым; какой тест это поймает; нужен ли новый.
6. **Ворота автономии:** сверься с матрицей ниже — можно ли делать без
   подтверждения.

## Матрица автономии

| Ситуация | Действие |
|---|---|
| Реализация шага утверждённого плана `docs/plans/*` | делать |
| Написание/расширение тестов | делать |
| Рефакторинг файлов, уже затронутых задачей (без смены поведения) | делать |
| Найден баг: есть воспроизводящий тест, фикс локален | делать + отметить в отчёте |
| Тюнинг defines в пределах, указанных планом | делать |
| Новая npm/pip зависимость | предложить, ждать |
| Изменение shared-типов сверх того, что требует план | предложить, ждать |
| Изменение геймплейного баланса вне плана | предложить, ждать |
| Правка текста самих `docs/plans/*` (кроме статуса/«Отклонений») | предложить, ждать |
| Найден конфликт док ↔ код или док ↔ док | остановиться, доложить, спросить |
| `client/src/map/**` (freeze), домен Gemini | не трогать без явного запроса |
| Смена архитектурного решения аудита, удаление функциональности | только пользователь |
| push, force-push, история | только пользователь |

Правило разрешения сомнений: **необратимое или расширяющее скоуп → спросить;
обратимое в рамках задачи → сделать и явно показать в отчёте.** Вопрос
пользователю формулируется с вариантами и рекомендацией, не открытым «как быть?».

## Протокол реализации механики (feature pipeline)

1. Взять план (`docs/plans/NN_*.md`) или оформить мини-план по шаблону
   Task Breakdown (TEMPLATES.md), если задачи нет в планах.
2. **Тесты-сначала:** каждый критерий приёмки → красный тест
   (шаблон TDD в TEMPLATES.md). Кампания-смок — если механика влияет на
   многомесячную динамику.
3. Реализация минимальными вертикальными срезами: тип → команда/тик →
   схема LLM → UI → данные. Каждый срез компилируется и тестируется.
4. Прогнать чек-лист ревью (TEMPLATES.md) на собственный дифф.
5. Верификация (STACK_PLAYBOOK.md, раздел «Верификация»).
6. Док-футпринт: TODO/DECISIONS/план-статус/системный док.
7. Коммит(ы) с осмысленными сообщениями; отчёт по шаблону.

## Протокол рефакторинга

Отличие от фичи: поведение НЕ меняется — и это доказывается.

1. Зафиксировать поведение: существующие тесты зелёные; если зона не покрыта —
   сначала характеризационные тесты (как есть, даже если поведение «странное»).
2. Рефакторить шагами, после каждого — зелёные тесты. Не смешивать рефакторинг
   и изменение поведения в одном коммите.
3. Детерминизм-проверка: same-seed кампания до/после даёт идентичное состояние
   (если рефакторинг в симуляции).
4. Если по пути найден баг: НЕ чинить молча внутри рефакторинга — отдельный
   красный тест + отдельный коммит фикса (до или после серии рефакторинга).

## Протокол работы с данными и пайплайном

1. Ручная правка `server/data/**` и `scripts/map/out/**` запрещена — данные
   меняются правкой скриптов/конфигов пайплайна и регенерацией.
2. После регенерации: валидатор данных зелёный; смок «createGame + 12 месяцев»
   проходит; диффы просмотрены на аномалии масштаба (население/ВВП стран ±).
3. Изменение схемы данных = изменение Zod-схемы загрузки + миграционный шаг
   в пайплайне + запись в DECISIONS.

## Протокол обращения с ошибками и неожиданностями

- Тест упал не по твоей теме → не «поправить, чтобы прошёл», а понять причину;
  флаки/предсуществующий провал — доложить, зафиксировать в TODO.
- Код противоречит доке → остановка, доклад, вопрос (правило AGENTS.md).
- Обнаружен дефект конституции в существующем коде (Map в state, константа в
  тике...) → не чинить в рамках чужой задачи; записать в TODO со ссылкой на
  правило; исключение — если дефект блокирует текущую задачу.
- Вывод команды подозрительно обрезан → перенаправить в файл и читать файл.

## Протокол против регрессии (итеративная работа, UI и с ИИ-реализатором)

Зафиксирован 2026-07-12 после реального регресса в UI-редизайне: в длинной
итеративной сессии агент терял ранние ограничения (повторно возвращал уже
удалённое), сдавал непроверенный визуально результат и скатывался в
механическое «двигание по списку». Причина — не «недостаточно внимания», а
отсутствие внешних лесов. Меры:

1. **Живой spec + список «НЕ возвращать».** Решения и удалённые элементы
   фиксируются явно (в плане/доке), с блоком «УБРАНО — не возвращать».
   Перечитывается каждую итерацию. Единственная надёжная защита от
   drift-регрессий на длинном контексте.
2. **Обязательный визуальный шаг.** Не сдавать UI, который не видел глазами:
   рендер → скриншот → критика перед показом. Если инструмент скриншота падает
   — обойти (заглушить анимации и снять кадр; другой рендерер), а не подменять
   визуальную проверку одними числами.
3. **Отдельный проход-критик.** После генерации сменить «шляпу» на ревьюера:
   «оцени как новый игрок с целью проекта; что не так?». Отдельный шаг, лучше
   на более высоком reasoning effort — критика качества это «think hard», а не
   механика.
4. **Мелкие точечные диффы вместо полных rewrite.** Полное переписывание файла
   реинтродуцирует уже убранное; точечная правка обозрима и не регрессирует
   соседнее.
5. **Закреплённые эталоны.** Держать референс (скриншот/утверждённый мокап) и
   явно сверяться с ним каждую итерацию.
6. **Долговременные правила.** Повторяющийся фидбек кодировать в durable-правила
   (память/роль `.claude/agents/ui-reviewer.md`), а не держать в контексте
   сессии.
7. **Критерии готовности на каждый элемент** + не поддакивать: держать
   собственное аргументированное мнение, предлагать альтернативы (см.
   `.claude/agents/ui-reviewer.md`, «Не скатываться в режим исполнителя списка»).

**Когда план исполняет другая модель (Sonnet 5 и т.п.):** те же леса
переносятся в сам план — каждый срез несёт (а) замороженный эталон + список
«не возвращать», (б) критерии приёмки, (в) обязательный визуальный QA-шаг,
(г) референс-скриншоты. Тогда реализатор не регрессирует тихо даже на длинном
контексте. Рекомендуемый reasoning effort реализатора: `high` по умолчанию,
`xhigh` на архитектурных срезах (фундамент/рефакторинг), `medium` на рутине.

## Протокол завершения сессии

1. Нет незакоммиченных изменений (либо явно доложено, что и почему осталось).
2. Док-футпринт выполнен (самопроверка: «я трогал /docs?»).
3. Отчёт по шаблону: сделано / не сделано / отклонения / следующий шаг.
4. Если задача не завершена — состояние зафиксировано так, чтобы холодная
   сессия продолжила: запись в плане («Отклонения/прогресс») или TODO.
