# 08 — Война, волна 1: оккупация ≠ аннексия, мир, потери, долг

Приоритет: P1 — связный контур «война имеет цену и итог» поверх уже
работающих систем. Четыре механики намеренно в одном плане: они замыкаются
друг на друга.
Статус: **план замкнут 2026-07-11** — все 4 шага реализованы (Шаг 1
оккупация, Шаг 3 потери, Шаг 2a warScore, Шаг 4 госдолг, Шаг 2b мир +
аннексия/`transferRegion`). Война имеет полный жизненный цикл: объявление →
фронт/оккупация → потери → warScore → мир с аннексией по очкам. Остаточные
обогащения (LLM-`PeaceTerms`, команда `default`, War Phase 3) — вне этого
плана. Логика-трек: `docs/plans/11_MVP_ROADMAP.md`.
Зависимости: 01 (transferRegion), 03 (команды/модификаторы/defines).

## 1. Оккупация ≠ аннексия

**Проблема:** `WarTick.ts:119` меняет `region.ownerCountryId` напрямую —
захваченный регион мгновенно становится легально чужим: платит налоги
захватчику, перекрашивается навсегда; мира «верни оккупированное» не
существует. Любая долгая война необратимо перекрашивает карту.

**Модель:**
- `Region.occupiedBy?: string` поверх `ownerCountryId`.
- Война двигает ТОЛЬКО оккупацию; владение двигает только мирный договор
  (командой `transferRegion`).
- Эффекты оккупации: доход/добыча региона идут оккупанту с штрафом
  (коэффициент в defines), стабильность региона падает (модификатор).
- Конец войны: не аннексированное по договору — оккупация снимается.
- Карта: оккупация — заливка цветом оккупанта со штриховкой (у клиента
  уже есть паттерн оккупационных оверлеев 1946).

## 2. Цели войны, war score, мирные договоры

**Проблема:** война бинарна (идёт/не идёт), `peace` — одно действие LLM без
условий. Некуда «выигрывать».

**Модель:**
- `War.warScore: number` (−100..100) — движок считает из: флипов оккупации
  (`territoryFlips` уже есть), соотношения потерь, длительности (истощение
  тянет к миру). Формула в defines.
- Мир — структура, а не сигнал:
  ```ts
  interface PeaceTerms {
    annexations: { regionId: number; to: string }[];
    reparations?: { from: string; to: string; amount: number };
    puppet?: string;
    demilitarize?: string;
  }
  ```
- LLM предлагает договор; валидатор проверяет «по средствам ли» текущего
  warScore (стоимость условий в очках — defines). Слишком жадный договор
  отклоняется с причиной — модель предлагает скромнее.
- Применение: команда `makePeace(warId, terms)` — annexations через
  `transferRegion`, репарации — из казны в казну, снятие оккупаций,
  `war.active = false`.
- Белый мир по таймауту/обоюдному истощению — детерминированный fallback,
  если LLM игнорирует затухшую войну N месяцев (порог в defines).

## 3. Потери → демография

**Проблема:** война никого не убивает — population и manpower не трогаются.
На горизонте 1836–2100 мировые войны обязаны оставлять демографические ямы.

**Модель (v1):**
- WarTick начисляет месячные потери сторонам из соотношения сил и числа
  контактных регионов (коэффициенты в defines).
- Потери списываются: с `military.activePersonnel` (в первую очередь),
  с `population` регионов фронта (гражданские + мобилизационная база),
  с `military.manpower` страны.
- `War.casualties: { [countryId]: number }` — накапливается, участвует в
  warScore и в промте LLM (готовый мировой факт: «X потеряла N человек»).
- PopulationTick уже существует — восстановление идёт естественным ростом,
  яма на десятилетия получается сама.

## 4. Госдолг

**Проблема:** `EconomyState.debtInterest` существует, но самого долга нет —
висящий провод. Война без займов не финансируется, дефолтов не бывает.

**Модель (v1):**
- `EconomyState.debt: number`. Дефицит бюджета покрывается ростом долга
  (казна не уходит в минус бесконечно: ниже нуля → конвертация в долг).
- `debtInterest = debt × interestRate` (ставка в defines; выше при низкой
  legitimacy/stability — одна формула).
- Порог долг/ВВП → модификатор (штраф росту) + детерминированный мировой
  факт «X на грани дефолта» (план 02, шаг 4). Сам дефолт отыгрывает LLM
  (списание долга + тяжёлые модификаторы) — команда `default(countryId)`.
- Репарации из п.2 могут выплачиваться в долг.
- AiBehaviorTick: правило аустерити уже смотрит на treasury — согласовать
  с долгом (аустерити при долг/ВВП выше порога).

## Порядок реализации внутри плана

1 (occupiedBy) → 3 (потери; нужен фронт из 1) → 2 (мир; нужны score из 1+3)
→ 4 (долг; независим, можно параллельно).

- [x] Мир возвращает неаннексированную оккупацию; аннексия по договору переносит владение через transferRegion (тест). — **Шаг 2b реализован 2026-07-11**: `WarService.applyPeaceTerms` аннексирует по бюджету warScore, `transferRegion` (`occupation.ts` + командная обёртка) — единственная прод-мутация `ownerCountryId`. ### Найдено разведкой, важное для будущих заходов

- **`transferRegion` физически не существует в коде** несмотря на то, что
  план называет его готовой зависимостью планов 01/03 — оба формально
  реализованы, но именно эта команда — нет. Шагу 1 она не понадобилась (см.
  ниже), но Шаг 2 будет строить её с нуля, не переиспользовать.
- **Клиентского паттерна оккупационных оверлеев не существует** — тезис
  плана не подтвердился. Единственное упоминание "оккупации" в
  `client/src/**` — комментарий `GeoJsonLoader.ts:27-28` про запекание зон
  оккупации 1946 в `ownerCountryId` на этапе импорта сценарных данных
  (build-time, не рантайм-механика).
- `WarService.makePeace` уже содержит собственную детерминированную модель
  исхода (легитимность + репарации 10% при decisive victory) — Шаг 2 должен
  явно решить, заменяет ли `PeaceTerms.reparations` этот механизм или
  складывается с ним (не решено текстом плана).

### Шаг 1 — ключевое упрощение: не понадобился `transferRegion`

Без Шага 2 (аннексия по договору) абсолютно вся оккупация снимается миром —
«не аннексированное по договору — оккупация снимается» при отсутствующей
аннексии означает «снимается всегда». Реализовано:

- `Region.occupiedBy?: string | undefined` поверх `ownerCountryId`.
- `shared/src/utils/regionControl.ts::effectiveController` — единая точка
  «кто сейчас фактически контролирует регион».
- `server/src/simulation/war/occupation.ts` — `setRegionOccupation` (ставит/
  снимает `occupiedBy` + `add`-модификатор `-20` на `Region.stability` через
  `commands/modifiers.ts`, переиспользует существующий атрибут `"stability"`
  для `target.kind:"region"` — белый список не привязан к форме сущности) +
  `revertOccupationForWar` (снимает оккупацию только конкретной войны).
- `WarTick.ts` — фронт (`isAttackerRegion`/`isDefenderRegion`/поиск
  контактного соседа) идёт по `effectiveController`, не `ownerCountryId`
  (иначе граница застревает на довоенной линии после первой оккупации).
  Флип вызывает `setRegionOccupation`, не мутирует `ownerCountryId` напрямую.
- `WarService.makePeace` — вызывает `revertOccupationForWar` сразу после
  `war.active = false`.
- `ResourceTick.ts` — единственный тик, переведённый на редирект дохода
  оккупанту (`countryRegions` по `effectiveController` + штраф
  `OCCUPATION_EXTRACTION_PENALTY=0.5`).

**Осознанно суженный периметр «доход/добыча — оккупанту».** Из 17+ мест,
читающих `ownerCountryId` как «легальный владелец = получатель дохода»,
переведён только `ResourceTick.ts`. **Не переведены**:
`aggregateCountryData.ts` (ВВП и население страны по-прежнему считаются по
`ownerCountryId` — оккупированный ВВП остаётся у легального владельца,
население оккупированного региона не становится населением оккупанта),
`MilitaryTick`/`PopulationTick`/`ResearchTick` (манпауэр/рождаемость/
исследовательские центры остаются на легальном владельце — план называет
только «доход/добычу»), соседство/дипломатия/рендер карты (вне периметра
критерия). Полный редирект ВВП потребовал бы разделения единой функции
`aggregateCountryFromRegions` на два разных фильтра для разных полей — более
рискованное изменение общей утилиты, не требуется критерием приёмки.

**Реальный читатель `region.stability` через `effectiveValue()` не
заведён** — модификатор оккупации ставится и снимается корректно
(тестируется напрямую через `game.modifiers`), но ни один тик пока не читает
`region.stability` через `effectiveValue()` (потребовало бы протащить
`game`/`modifiers` в `PopulationTick.ts`, которая их сейчас не получает) —
тот же класс сигнатурного изменения, что нужен для Шага 4, не требуется
критерием приёмки Шага 1.

**Клиентская визуализация оккупации** (штриховка и т.п.) — интерфейс
заморожен решением пользователя (2026-06-23), ни один критерий приёмки не
требует UI.

### Шаги 2-4 — отложены целиком

- **Шаг 2** (war score, `PeaceTerms`, мирные договоры) — самый крупный
  риск: первое составное `data`-поле LLM-контракта (массив объектов +
  опциональный вложенный объект), требует обязательного живого прогона
  против реального Gemini API (контракт только что стабилизирован планом 02
  с 3 подтверждёнными живыми находками расхождений диалекта structured
  output); коллизия с существующей моделью `WarService.makePeace` не
  разрешена планом; `transferRegion` пришлось бы строить здесь. Минимум 6
  существующих тестов вызывают `peace` без `data` — перестанут тайпчекаться.
- **Шаг 3** (потери → демография) — по порядку плана зависит от score Шага 2
  (`War.casualties` нужен и там, и в промте) — без потребителя это мёртвое
  поле, логичнее вместе с Шагом 2.
- **Шаг 4** (госдолг) — нерешённая гейм-дизайн развилка (`treasury`-в-минусе
  vs конвертация в `debt`, коллидирует с существующим тестом
  `WarService.test.ts` про репарации при отрицательной казне) и
  архитектурное решение (протащить `game.modifiers` через сигнатуру
  `economyTick()`) — оба требуют явного решения пользователя. Независим от
  остальных шагов, можно брать отдельным заходом в любой момент.
