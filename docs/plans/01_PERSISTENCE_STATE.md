# 01 — Сохранения и гигиена GameState

Приоритет: **P0** — блокирует смысл всей остальной работы (кампанию нельзя сохранить).
Статус: реализовано (2026-07-10), см. `docs/ARCHITECTURE.md` §"Сохранения" и раздел "Отклонения при реализации" ниже.
Зависимости: нет. Остальные планы опираются на этот.

## Проблемы (текущее состояние)

1. **Сохранений не существует.** `server/src/game/GameStore.ts` — module-level
   переменная с одной игрой. Перезапуск сервера = потерянная кампания.
   `docs/ARCHITECTURE.md` называет «savegame» источником истины — его нет.
   Синглтон также блокирует слоты и вторую параллельную игру.

2. **Активный баг: протухающий `regionIndex`.** Индекс строится один раз в
   `createGame` (`server/src/game/CreateGame.ts:88`), но
   `server/src/simulation/war/WarTick.ts:119` меняет `region.ownerCountryId`
   при фронтовых флипах — индекс не перестраивается. Итог: `ResourceTick`
   (единственный потребитель, `server/src/simulation/resources/ResourceTick.ts:13`)
   начисляет ресурсы по довоенной карте владения.

3. **Несериализуемое поле в состоянии.** `GameState.regionIndex: Map<string, number[]>`
   (`shared/src/types/GameState.ts:20`) сериализуется в `{}` при `res.json(game)` —
   клиент получает битое поле. Корень: производное состояние хранится внутри
   игрового состояния.

4. **Недетерминизм.** Единственный `Math.random` в симуляции —
   генерация id в `MapFeatureService.generateId()`. Политики seeded RNG нет.

5. **Нет версии сейва** — любое изменение типов сломает будущие сохранения молча.

## Целевая модель

**Правило: GameState — только plain-JSON данные.** Ни Map, ни Set, ни классов,
ни функций. Всё производное (индексы) вычисляется при загрузке/на лету.

### Шаг 1. Убрать `regionIndex` из GameState

- Удалить поле из `shared/src/types/GameState.ts`.
- `ResourceTick` получает регионы так же, как остальные тики
  (фильтр или пересобираемый в начале `simulateMonth` локальный индекс —
  при 1366 регионах × 128 странах это микросекунды).
- Опционально: один локальный индекс `Map<countryId, Region[]>` строится
  в начале `simulateMonth` и передаётся во все тики (заменяет и
  повторяющиеся `regions.filter(r => r.ownerCountryId === ...)` в
  EconomyTick/PopulationTick/MilitaryTick/ResearchTick/aggregateCountryData).
  Он живёт один тик — протухнуть не успевает (WarTick идёт после по-страновой
  петли; после WarTick индекс не использовать или пересобрать).

### Шаг 2. Сейвы

- `SaveService` на сервере: каталог `server/data/saves/`, файл =
  `JSON.stringify({ version, savedAt, game })`.
- API: `POST /game/save { slot }`, `POST /game/load { slot }`,
  `GET /game/saves` (список слотов с метаданными: дата, страна игрока,
  игровая дата), `DELETE /game/saves/:slot`.
- Автосейв: в конце каждого успешного `advanceMonth` — слот `autosave`
  (перезаписываемый). Синхронной записи достаточно (файл ~2 МБ).
- `version: number` — константа SAVE_VERSION; при загрузке несовпадение →
  явная ошибка (миграции сейвов — потом, сейчас достаточно честного отказа).
- Транзиентные поля НЕ сохранять или обнулять при загрузке:
  `llmContext`, `llmResponse` (кэш последнего ответа — можно оставить),
  `pendingLlmActions`.
- UI: панель слотов в клиенте (кнопки в `GameView` — сохранить/загрузить).

### Шаг 3. Seeded RNG

- `shared/src/utils/rng.ts`: mulberry32 или splitmix32 (30 строк, без зависимостей).
- `GameState.rngState: number` — сериализуемое состояние генератора.
- Заменить `Math.random` в `MapFeatureService.generateId()` на счётчик:
  `GameState.nextFeatureId: number` → id вида `mf-000123`.
- Правило на будущее: вся случайность симуляции — только через `game.rng`.

### Шаг 4 (опционально, после 03). Команда `transferRegion`

Единственная точка смены владельца региона:
`transferRegion(game, regionId, newOwnerId)` — меняет `ownerCountryId`,
пишет событие, инвалидирует локальные индексы. Все места, меняющие владение
(WarTick-флипы, annex из LLM), переводятся на неё. Детали — план 03 и 08.

## Критерии приёмки

- [x] В GameState нет Map/Set; `JSON.parse(JSON.stringify(game))` эквивалентен game.
- [x] Сохранение → перезапуск сервера → загрузка → `advanceMonth` работает.
- [x] Тест: после флипа региона в WarTick ResourceTick начисляет ресурсы новому владельцу.
- [x] Тест: два прогона симуляции с одним seed дают идентичное состояние (глубокое сравнение).
- [x] Автосейв появляется после каждого хода.

## Отклонения при реализации

Реализовано 2026-07-10 по протоколам `docs/agent/PROTOCOLS.md`, вместе с
первыми fitness-функциями конституции (`server/src/__tests__/architecture.test.ts`,
реестр — `docs/agent/ARCHITECTURE_GUARDRAILS.md`).

- **Шаг 1 — плоский вариант, без опционального общего локального индекса.**
  План предлагал вторым (явно «опционально») вариантом собирать
  `Map<countryId, Region[]>` один раз в начале `simulateMonth` и передавать
  его во все тики взамен пяти повторяющихся
  `regions.filter(r => r.ownerCountryId === ...)`. Не сделано — ни один
  критерий приёмки этого не требует, план сам называет это
  оптимизацией-не-необходимостью («при 1366×128 это микросекунды»); фикс
  ограничен `ResourceTick.ts`, который приведён к тому же паттерну filter,
  что уже используют `EconomyTick`/`PopulationTick`/`MilitaryTick`/
  `ResearchTick`. `shared/src/utils/buildRegionIndex.ts` удалён целиком
  (единственный вызывающий пропал).
- **Найденный по пути и исправленный блокер (не в тексте плана дословно):**
  `MapFeatureService.createMapFeature()` проставлял `createdAt` через
  `new Date().toISOString()` (wall-clock) — два прогона `createGame()` с
  одинаковым seed давали разные `createdAt` у одинаковых стартовых фич,
  что ломало критерий приёмки «два прогона с одним seed → идентичное
  состояние». Приведено к `this.game.currentDate` (игровое время, правило
  конституции 5). Исправлено в рамках задачи, так как блокировало её
  acceptance-критерий (протокол ошибок и неожиданностей, PROTOCOLS.md).
  `removeExpiredFeatures()` (тот же файл, сравнение `expiresAt` с
  `new Date().toISOString()`) — **не тронуто**: `expiresAt` нигде не
  выставляется в проде (только в тестах), ничего не блокирует; занесено в
  `docs/TODO.md` одной строкой, ушло в белый список grep-теста правила 5 с
  комментарием-причиной.
- **`GameState.version` не добавлено** как отдельное поле состояния — версия
  сейва (`SAVE_VERSION`) живёт в обёртке файла (`{version, savedAt, game}`,
  `shared/src/types/SaveFile.ts`), не внутри самого `GameState`. План это и
  описывал («файл = `{version, savedAt, game}`»), просто уточнено явно, чтобы
  не читалось как пропуск.
- **`SaveService` — модуль plain-функций, не класс** (`server/src/game/SaveService.ts`)
  — следует правилу `docs/agent/STACK_PLAYBOOK.md` («новых сервис-классов не
  плодить», новая логика — функции), тот же стиль, что у `GameStore.ts`.
- **Seeded RNG (`shared/src/utils/rng.ts`, `GameState.rngState`) добавлен как
  инфраструктура без текущего вызывающего в игровой логике** — план сам так
  и формулирует Шаг 3 («правило на будущее»). Единственный текущий источник
  недетерминизма (`MapFeatureService.generateId()`) заменён отдельным
  счётчиком `GameState.nextFeatureId` (`mf-000123`), не через `rngState`, —
  тоже дословно по тексту плана.
- **Шаг 4 плана (команда `transferRegion`) не реализован** — план сам
  помечает его «опционально, после 03» (план 03 — команды/модификаторы — ещё
  не начат, `docs/plans/README.md` фиксирует порядок `01 → 02 → 03 → ...`).
  Не урезание скоупа, а следование уже утверждённой зависимости планов.

**Проверено:** tsc ✅ (`server`/`client`), vitest server ✅ (428/429 — один
красный тест `campaignSmoke.test.ts` про калибровку ВВП/чел бедных стран,
заранее известная находка 2026-07-06, не связана с этой задачей и намеренно
оставлена красной, чтобы не потерять её). Same-seed детерминизм-тест
(`server/src/game/__tests__/CreateGame.test.ts`) подтверждён: два прогона
`createGame(seed) + 12 месяцев simulateMonth` дают глубоко идентичное
состояние. Живая проверка (`curl`, dev-сервер): `POST /game/start` →
`POST /game/save` → `GET /game/saves` → `POST /game/load` →
`POST /llm/response` → `POST /game/next-turn` (дата продвинулась) →
`DELETE /game/saves/:slot` — весь цикл отработал, автосейв (`autosave.json`)
подтверждён отдельным запросом состояния.
