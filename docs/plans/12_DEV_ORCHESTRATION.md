# 12 — Оркестрация разработки Geopolis

Как ведётся разработка v1 по дорожной карте (`11_MVP_ROADMAP.md`): кто запускает
задачи, кто проверяет, на каких моделях, и когда крупную задачу выносить в
отдельную сессию. Процессный план этапа реализации (после завершённого дизайна:
`docs/CONCEPT.md` + `docs/PRIMITIVES.md`).

## Роль оркестратора

**Opus-сессия «оркестратор»** ведёт разработку по дорожной карте, милстоун за
милстоуном. Сам фичи не пишет — **распределяет, проверяет, интегрирует,
координирует**. Тонкий: работает через diff'ы, статусы и проверки, не тащит весь
код в контекст (та же философия, что «не слать весь мир в LLM»).

## Три уровня исполнения — по размеру задачи

| Уровень | Кто | Когда | Модель |
|---|---|---|---|
| **Субагент** | Оркестратор запускает сам (Agent/Workflow) | Узкое, read-heavy, влезает в один контекст, возвращает результат | Haiku (рутина/поиск) · Sonnet (узкая реализация) |
| **Отдельная сессия** | Оркестратор ПОДСКАЗЫВАЕТ — пользователь открывает | Крупная система: свой worktree, долгая итерация, человек-в-петле | Своя (Opus/Sonnet) |
| **Codex-аудит** | Оркестратор подсказывает — пользователь открывает Codex | Приёмка крупного милстоуна / повышенный риск | Codex (другая модель) |

## Критерий «когда подсказать отдельную сессию»

Оркестратор помечает задачу как «крупную → отдельная сессия», если срабатывает
**любой** триггер:
- Это **целый милстоун** из карты (1–6).
- **Cross-module** — трогает 2+ из `client`/`server`/`shared`.
- **Нужен свой worktree** — правит файлы параллельно с другой работой.
- **Долгая итерация** — десятки ходов, свой контекст (субагент не удержит).
- **Человек-в-петле** — по ходу возникают продуктовые развилки.
- **Security / архитектура / миграция.**

Иначе (верификация, поиск, ревью, узкая правка 1–3 файлов, data-скрипт) →
**субагент**, оркестратор делает сам.

**Как выглядит подсказка** (как для дизайн-Фазы 3): оркестратор генерирует
готовый промт (через `prompt-architect`) и говорит, *когда* пора открыть сессию и
*какую*: «Милстоун 2 — крупный (cross-module, свой worktree, человек-в-петле).
Рекомендую сессию `claude/milestone-2-politics`. Вот промт: […]. Открой — приму,
прогоню тесты и ревью, доложу.»

## Проверка — двухуровневая, независимая

| Уровень | Кто | Что ловит | Когда |
|---|---|---|---|
| **1. Claude-внутренний** | verify-агент (`tsc --noEmit` / `npm test` / `lint` / `build` / python-валидаторы) + `code-reviewer` субагент | Регрессии, стиль, очевидные баги | Всегда, каждая под-задача |
| **2. Codex-внешний аудит** | Codex (другая модель), read-only, свой worktree | Слепые зоны Claude: контракт-гапы, архитектурные противоречия, недооценённая сложность | Крупные милстоуны / повышенный риск |

**Почему Codex, а не ещё один Claude-субагент:** Claude-исполнитель и
Claude-ревьюер разделяют системные слепые зоны — одинаковые паттерны, одинаковые
пропуски. Codex их не разделяет — ловит то, что вся Claude-цепочка пропустит. Не
«второе мнение того же рода», а другая архитектура взгляда. Доказано в дизайн-цикле:
Codex-ревью Фазы 2 нашёл 7 критичных контракт-гапов (K1–K7), которых Claude не
увидел → 5 правок.

**Как подключается Codex:** триггер — милстоун закрыт + Claude-verify прошёл →
перед мержем оркестратор генерирует задачу для Codex (как
`.agent/plans/codex-design-review-task.md`): read-only к продукту, проверяет
требования+diff по коду, НЕ принимает объяснения Claude-исполнителя за
доказательство, пишет отчёт с градацией (критичные/средние/мелкие). Codex работает
в своём worktree (`codex/<task>`). Оркестратор Codex не запускает силой —
подсказывает пользователю + даёт задачу, потом принимает отчёт и превращает
находки в правки.

## Цикл на один милстоун

1. **Планирую** — читаю милстоун (`план 11`) + зависимости, разбиваю на под-задачи.
2. **Классифицирую** каждую: субагент или отдельная сессия.
3. **Запускаю субагентов** сам / **подсказываю сессии** для крупного.
4. **Принимаю работу** → Уровень 1 (Claude-verify: тесты + code-review).
5. **Крупный/рисковый** → Уровень 2 (подсказываю Codex-аудит, принимаю отчёт).
6. **Находки Codex** → правки → повторная проверка.
7. **Интегрирую** принятое, отбраковываю сырое; координирую ветки/worktree.
   **Мерж в `main` — только с разрешения пользователя.**

## Привязка к дорожной карте (`план 11`)

- **Милстоун 0 (вертикальный срез)** — одной фокус-сессией (узкий, целостный,
  доказывает валидатор примитивов) + субагенты на верификацию. + Codex-аудит на
  приёмке (это доказательство ядра — риск высокий).
- **Милстоуны 1–6** — каждый = отдельная сессия (крупная система). Оркестратор
  подсказывает открыть по готовности зависимостей, даёт промт, принимает, гоняет
  Codex-аудит на крупных.
- **Data-долг** (демо-состав ~1399 регионов, морские театры, координаты идеологии)
  — субагенты / дата-сессии параллельно, не блокируют милстоуны.
- **Инфра-долг** (телеметрия токенов, кап chronicle) — субагенты по ходу.
- **Гейт лицензий** — оркестратор держит как блок релиза, напоминает перед
  публикацией.

## Модели по роли

- **Opus** — оркестратор, архитектура, ревью, интеграция.
- **Sonnet** — реализация фич.
- **Haiku** — рутина, поиск, механические правки, data-скрипты.
- **Codex** — независимый адверсариальный аудит (другая модель).
- Effort (`low`→`max`) — по сложности задачи.

## Принципы

- **Автор не судья своей работе** — проверку делает независимый агент/сессия, на
  крупном последнее слово у другой модели (Codex).
- **Дёшево где можно** — Haiku/Sonnet на рутину и реализацию, Opus только на
  архитектуру/ревью/интеграцию.
- **Один worktree = одна изменяющая задача** (AGENTS.md) — крупное уходит в
  отдельные сессии со своими ветками, оркестратор координирует перепиской.

## Честные границы

- Субагенты живут в контексте оркестратора — крупное уходит в отдельные сессии
  (их открывает пользователь; оркестратор подсказывает и готовит промт).
- Программный запуск полноценных сессий ограничен — оркестратор координирует их
  перепиской (`send_message` между сессиями), а не запускает силой.
- Codex тоже запускает пользователь — оркестратор готовит задачу и принимает отчёт.

## Как запустить оркестратор

1. Дизайн-цикл (ветка `claude/design-partner-audit`: `CONCEPT.md` + `PRIMITIVES.md`
   + дорожная карта + этот документ) влить в `main` или работать от него — решение
   пользователя.
2. Открыть новую Opus-сессию в рабочем дереве разработки.
3. Дать ей промт-задание оркестратора (вход: `docs/plans/11` + `docs/plans/12` +
   `docs/CONCEPT.md` + `docs/PRIMITIVES.md` + `AGENTS.md`; старт с милстоуна 0).
4. Оркестратор ведёт милстоун 0, подсказывает сессии/Codex-аудит по критериям выше.
