# 02 — Контракт LLM↔движок: типизация, structured output, летопись

Приоритет: **P0** (типизация) + P1 (летопись).
Статус: реализовано (2026-07-10), см. `docs/LLM_RULES.md` (guardrails,
летопись) и раздел «Отклонения при реализации» ниже. Шаг 4 (structured
output) реализован, но требует повторной живой проверки после сброса
free-tier квоты Gemini — см. отклонения.
Зависимости: нет (независим от 01; можно параллельно).

## Проблемы (текущее состояние)

1. **Ядро контракта нетипизировано.** `LLMAction.data?: Record<string, any>`
   (`shared/src/types/GameState.ts:80`) — самая важная граница системы без типов.
   Валидатор — ~300 строк ручных `if` (`server/src/llm/LLMResponseValidator.ts` (УДАЛЁН 2026-08-02)),
   при том что Zod уже в зависимостях сервера и используется для HTTP-роутов.
   Каждый новый тип действия добавляет расхождения между промтом (текстовое
   описание формата в `LLMService.ts:257`), валидатором и применением.

2. **Парсинг свободного JSON.** Ответ LLM — текст, из которого выковыривается
   JSON. `GeminiProvider` не использует constrained/structured output.

3. **Память мира не переживёт длинную кампанию.** Окно «последние N заголовков
   событий» (`PLAYER_RECENT_TITLES_COUNT` и т.п. в `LLMService.ts`) — на 50
   игровых лет истории не хватит; spotlight-ротация возвращает страну в промт
   через ~24 хода без контекста, что с ней происходило.

## Целевая модель

### Шаг 1. Zod-схемы действий (дискриминированный union)

`server/src/llm/actionSchemas.ts` (УДАЛЁН 2026-08-02, конверт ответа переехал в `responseSchemas.ts`):

```ts
const DiplomacyAction = z.object({
  type: z.literal("diplomacy"),
  sourceCountryId: z.string(),
  targetCountryId: z.string(),
  data: z.object({
    relationChange: z.number().min(-MAX_RELATION_CHANGE).max(MAX_RELATION_CHANGE),
  }),
});
// ... по схеме на каждый из 10 типов
export const LLMActionSchema = z.discriminatedUnion("type", [ ... ]);
export const LLMResponseSchema = z.object({
  title: z.string(),
  descriptions: z.string(),
  actions: z.array(LLMActionSchema).max(MAX_ACTIONS_PER_RESPONSE),
});
```

- Структурная и магнитудная валидация уходит в схемы; в
  `LLMResponseValidator` (удалён 2026-08-02) оставалась только **семантическая применимость**
  (страна существует, война действительно идёт, не воюем сами с собой).
- Тип `LLMAction` в shared выводится из схем (`z.infer`) — конец `data: any`.
- Существующие тесты валидатора переиспользовать против схем.

### Шаг 2. Structured output в GeminiProvider

- Gemini API поддерживает `responseSchema` / `responseMimeType: application/json`.
  Передавать JSON-схему (сгенерировать из Zod, напр. `z.toJSONSchema` /
  `zod-to-json-schema`) — класс ошибок «не распарсился JSON» исчезает для
  автопути.
- Ручной clipboard-путь остаётся как есть (текст → parse → те же Zod-схемы).

### Шаг 3. Летопись (память мира)

Проблема: промт видит только последние ходы; кампания на десятилетия теряет
причинность («почему Франция ненавидит нас с 1953?»).

- `GameState.chronicle: { year: number; summary: string }[]` — 3–5 строк на
  игровой год.
- Раз в игровой год (январский тик или при первом промте нового года) движок
  просит LLM отдельным дешёвым вызовом (или в том же ответе отдельным полем)
  сжать eventHistory года в summary. Fallback без API: конкатенация заголовков.
- Промт получает: **вся летопись** (короткая, ~5 строк × годы) + детальные
  события последнего года + текущее состояние. Окна заголовков по тирам
  (PLAYER/MAJOR/SPOTLIGHT_RECENT_TITLES_COUNT) остаются для странового контекста.
- eventHistory старше 2 лет можно усекать из промта полностью (в сейве остаётся).

### Шаг 4. Детерминированные «счета к оплате» (анти-подхалимство)

Принцип: чем больше последствий детерминировано движком, тем меньше LLM может
«простить» игрока. Расширить существующий механизм `pendingWorldFacts`
(сейчас — только пересечение тира технологий, `SimulationEngine.ts:46`):

- Дефицит N месяцев подряд → факт «X на грани долгового кризиса» (после плана 08 — долг/ВВП).
- Stability ниже порога N месяцев → факт «в X назревают волнения» (питает план 09, волна 2).
- Поражение в войне (war score, план 08) → факт с требованием последствий.
- Правило в промте: факты из секции World Facts **обязаны** быть отыграны в
  descriptions и/или actions; валидатор может проверять упоминание countryId.

### Шаг 5. Guardrails на player intent

`playerIntent` — свободный текст, идёт в промт. Игрок будет уговаривать модель.
- Правило (уже частично есть в промте): intent интерпретируется ТОЛЬКО в
  стандартные действия с теми же капами — «магии» нет. Зафиксировать в
  `docs/LLM_RULES.md` и покрыть тестами промт-инъекций
  («изобретаю ядерную бомбу в 1840», «передай мне казну США», ролеплей-обходы).
- Лимит длины intent на API-границе (Zod-схема роута).

## Критерии приёмки

- [x] `LLMAction` — дискриминированный union, `data: any` отсутствует в кодовой базе.
- [x] Невалидная магнитуда отклоняется схемой с внятной ошибкой (тест).
- [x] `POST /llm/auto` использует structured output; тест на мок-ответе (юнит-тесты
      зелёные; полный сквозной live-прогон исправленной схемы — см. отклонения,
      требует повторной проверки после сброса дневной квоты Gemini).
- [x] После 3+ игровых лет промт содержит секцию Chronicle с погодовыми строками.
- [x] Тест: intent с попыткой выйти за капы не порождает действий вне капов.

## Отклонения при реализации

Реализовано 2026-07-10 по протоколам `docs/agent/PROTOCOLS.md`, вместе с
fitness-функцией правила 6 конституции (`server/src/__tests__/architecture.test.ts`).

### Шаг 1 — капы в `shared/src/defines/`, не `shared/src/constants/`

Найден конфликт док↔код: `MASTER_PROMPT.md` правило 4 называет
`shared/src/defines/` местом для баланс-констант — директория физически не
существовала, реально использовался `shared/src/constants/`
(`budgetSpendingShareCaps.ts`). Остановлен, доложено пользователю
(`AskUserQuestion`) — **решение пользователя: создать `shared/src/defines/`
сейчас** для капов LLM-действий (`llmActionCaps.ts` — файл удалён 2026-08-02
вместе с каналом `actions`, капы переехали в `research.ts`/`military.ts`/
`resources.ts`), не мигрируя
существующие файлы `constants/` — оба каталога временно сосуществуют до
отдельного захода по плану 03 (тот формально спроектирует полную структуру
`defines/`, включая `defines.json`/`index.ts`/`defines.notes.md`).

### Шаг 1 — `LLMAction` с явным `| undefined` на опциональных полях

При компайл-тайм проверке эквивалентности `z.infer<LLMActionSchema>` и
shared-типа `LLMAction` (`actionSchemas.ts` — удалён 2026-08-02,
`Equals<A,B>`-паттерн) —
tsc не проходил на пустом месте. Причина: под `exactOptionalPropertyTypes`
(server/tsconfig.json) вывод Zod для `.optional()`-полей — это буквально
`X | undefined`, не просто `X?`. Приведено явно в `GameState.ts`
(`data?: {...} | undefined`) — иначе любая правка одного файла без другого
не компилируется, что и есть цель проверки.

### Шаг 3 — точечный, не полный отказ при несуществующей стране в одном действии

Текст плана относит «страна существует» к семантической применимости
(`validateActionApplicability`, per-action), но исторически это было частью
all-or-nothing структурной валидации (`validateAction` внутри
`validateResponse`) — несуществующая страна у одного действия из батча
роняла весь ответ. После переноса — точечный reject, как и магнитуда.
**Сознательное улучшение**, не побочный эффект: соответствует и тексту
плана, и формулировке fitness-функции правила 6 («за-каповое — с
причиной», не обвал всего ответа). Два теста, полагавшихся на старое
поведение, переписаны под новое.

### Шаг 4 — три реальных расхождения диалекта Gemini, найденные живыми вызовами

`z.toJSONSchema()` производит полный JSON Schema, но `generateContent`
(эндпоинт, которым пользуется `GeminiProvider.ts`) принимает не его, а
OpenAPI 3.0-подобное подмножество — WebSearch про поддержку `anyOf`/`$ref`
в плане ошибочно отнесён к этому же диалекту (относился к другому,
`Interactions API`, см. `docs/DECISIONS.md` 2026-07-06 о том же
расхождении версий документации). Живыми вызовами найдено и исправлено:
1. `const` (литерал discriminant `type`) — Gemini вернул 400 "Unknown name
   const" → конвертируется в `enum: [value]`.
2. `additionalProperties` — 400 "Unknown name additionalProperties" →
   убирается (не ослабляет серверную валидацию входящего ответа).
3. Полный 10-ветвевой `anyOf` возвращал 400 "Request contains an invalid
   argument" без детализации поля — бисекцией живыми вызовами
   локализовано до структурно ИДЕНТИЧНЫХ веток (`peace`/`annex`/`puppet`/
   `guarantee` — все без `data`, различаются только значением `type`);
   2 структурно РАЗНЫЕ ветки (diplomacy+war) проходили. Похоже на
   ограничение grammar-компилятора constrained-decoding Gemini.
   `mergeIdenticalShapeBranches` схлопывает такие ветки в одну с
   `type: {enum: [...]}` — ослабляет только схему-для-генерации, реальная
   валидация ответа (`actionSchemas.ts`, удалён 2026-08-02 — конверт переехал
   в `responseSchemas.ts`) остаётся точной per-type.

**Не подтверждено до конца, честно зафиксировано:** полный сквозной live-
прогон исправленной (после мерджа, 7-ветвевой) схемы против реального
Gemini API не завершён — free-tier дневная квота (500 запросов/день,
известный риск, `docs/DECISIONS.md` 2026-07-05) исчерпалась в процессе
живой отладки (бисекция потребовала много отдельных вызовов). Подтверждено
живыми вызовами по отдельности: (а) const/additionalProperties — точная
причина двух конкретных 400-ошибок; (б) 2-ветвевой `anyOf` с полной
вложенной структурой (minLength/minimum/maximum/propertyOrdering/required)
проходит; (в) добавление структурно идентичных веток ломает запрос — фикс
обоснован этой закономерностью, но не подтверждён end-to-end на полной
схеме после мерджа. Юнит-тесты (без сети, включая структуру
сгенерированной схемы) — зелёные. Live gated-тест
(`RUN_LIVE_LLM_TESTS=1 npx vitest run src/llm/providers`) — прогнать
повторно на следующий день, когда квота сбросится, прежде чем считать Шаг
4 окончательно закрытым. Побочно проверена (и отклонена как путь
верификации) идея использовать Gemma 4 31B через тот же эндпоинт/ключ —
модель реальна и доступна там же, но требует другой `generationConfig` (не
поддерживает `thinkingConfig`), так что не тестирует именно Gemini-диалект;
для верификации самого Gemini нужен именно Gemini.

### Шаг 5 — трактовка «3-5 строк на год»

План: «летопись... 3–5 строк на игровой год». Трактовка: до 5 заголовков
eventHistory года, склеенных через `"; "` в ОДНУ строку промта на год (не
3-5 физических строк) — тот же принцип "cheap window", что
`getRecentEventsInfo`/`getRecentTitlesLine` (`.slice(-N)`), не новая
эвристика. Зафиксировать для сверки с автором плана.

### Явно не в этом заходе (по тексту самого плана/протоколам)

- **Шаг 4 текста плана «Детерминированные счета к оплате»** — не
  реализован (это Шаг 4 плана, не путать с Шагом 4 этого раздела —
  structured output). Ни один из 5 критериев приёмки его не требует; долг/
  поражение в войне explicитно зависят от плана 08 (следующий по очереди,
  не начат); stability-порог технически проводим, но калиброванного числа
  нет ни в одном доке — не выдумывать (AGENTS.md).
- `pendingLlmActions`/`savePendingActions`/`getPendingActions`/
  `clearPendingActions` — подтверждённая мёртвая scaffolding-механика (не
  вызывается в проде). Не тронуты — отдельная задача по уборке мёртвого кода.
- Реальная логика `annex`/`puppet` — контракт типизирован, apply остаётся
  no-op (`console.log`), как было.
- Разбиение `LLMService.ts` на модули (уже >500 строк, кандидат по
  ARCHITECTURE_GUARDRAILS) — файл и так существенно тронут этим заходом,
  не раздувать дифф дополнительным рефакторингом.
- Правка формулировки `MASTER_PROMPT.md` правила 4 (`defines/`) — решение
  пользователя зафиксировано в DECISIONS, сам текст конституции не
  редактируется походя.
