# 04 — Ресурсы: deposit / extraction / output

Приоритет: P1.
Статус: реализовано (2026-07-11), см. `docs/ECONOMY.md` §"Добыча ресурсов",
`docs/ARCHITECTURE.md` §"Команды"/§"Модификаторы", `docs/LLM_RULES.md`
§"Экономика".
Зависимости: 03 (команды/модификаторы), 05 (расслоение данных — желательно, не обязательно).

## Проблемы (текущее состояние)

`region.resourceProduction` — одно число, означающее сразу три вещи:
геологический потенциал, текущую добычу и изменяемое состояние
(`ResourceTick.ts:47-53` истощает его на 0.01%/мес прямо в данных).

Следствия:
- нельзя отличить «мало нефти» от «нефть есть, добыча не развёрнута» и от
  «добыча разрушена войной»;
- нет механики стройки шахт («шахты рядом с месторождениями» из PROJECT.md
  невыразимы);
- LLM/события не могут безопасно менять производство — только перезаписать число.

Заготовка уже есть: `shared/src/types/resources/ResourceDeposit.ts` существует,
но не используется. Каталог `shared/src/data/resources/resourceCatalog.ts`
(«только сырьё, переделы — выход промышленности») — правильный, не менять.

## Целевая модель — три слоя

| Слой | Что | Где живёт | Кто меняет |
|---|---|---|---|
| **Deposit** | `{ resource, richness, techGate? }` — потенциал | данные сценария (regions) | почти никто: истощение медленно, открытие — событие |
| **Extraction** | уровень добывающих мощностей 0..N по ресурсу | GameState | команды: стройка, война, события, LLM |
| **Output** | добыча за тик | **не хранится** — вычисляется | никто |

Формула тика:
```
output = richness × extractionFactor(level) × infraBonus × techBonus × modifiers
```
Существующие бонусы ResourceTick (инфраструктура, домен industry, сектор
mining) сохраняются как множители; их коэффициенты — в defines (план 03).

### Шаги

1. Типы: `RegionDeposit { resource, richness }` в Region (переименовать/пере-
   использовать поле `resourceProduction` → `deposits`; миграция данных — скриптом
   пайплайна, см. шаг 4). `Region.extraction: Partial<Record<ResourceId, number>>`
   — стартовый уровень задаётся сценарием (сегодняшние значения производства
   нормировать в richness × стартовый level = текущий выход, чтобы баланс не
   сдвинулся в момент миграции).
2. ResourceTick: считает output по формуле, кладёт в stockpile. Истощение —
   на richness депозита, скорость в defines. Output за последний тик можно
   кэшировать в поле для UI (`lastOutput`), но оно производное — не источник.
3. Команды (план 03): `buildExtraction(regionId, resource, +1 level)` — с ценой
   из defines и проверкой «есть deposit»; `damageExtraction(...)` — для войны
   и событий; временные эффекты («забастовка −50% на 6 мес») — модификаторы.
4. Python-пайплайн: `fill_region_economy_1946.py` / `resource_geography.py`
   выдают deposits + стартовые extraction вместо одного числа.
5. LLM: действия ограничены командами шага 3 с капами (±1 level за ход,
   модификаторы из белого списка). Сырые числа производства LLM не пишет.
6. Связь с MapFeature (план 06): фича `mine` создаётся при `buildExtraction`
   в регионе — визуальное лицо уровня добычи.

### За скобками (сознательно НЕ делать сейчас)

- Цепочки переработки (боксит→алюминий, руда→сталь) — переделы остаются
  абстрактной «промышленностью страны».
- Логистика ресурсов между регионами.
- Эластичность мировых цен (спрос/предложение двигают цену) — следующий шаг
  Trade v2, отдельным заходом (~30 строк в TradeTick, см. бэклог 09).

## Критерии приёмки

- [x] `resourceProduction` как хранимое изменяемое число отсутствует; тики не мутируют данные месторождений (кроме медленного истощения richness).
- [x] Тест: buildExtraction увеличивает output следующего тика; damageExtraction уменьшает.
- [x] Тест: модификатор на добычу (например −50% на 6 мес) влияет и истекает.
- [x] Пайплайн регенерирует regions с deposits; суммарный стартовый output стран равен прежнему (±1%) — баланс не сдвинулся (фактически 0% дрейфа, см. «Отклонения при реализации»).
- [x] LLM-действие, пишущее произвольное число добычи, отклоняется валидатором.

## Отклонения при реализации

- **Порядок срезов**: Python-пайплайн (шаг 4 плана, «Срез 5» по изначальной
  разбивке) выполнен в **Срезе 1**, а не в конце — миграция
  `Region.deposits`/`extraction` в TS-типах немедленно ломала любой тест,
  создающий партию через `createGame()` на живом `regions.json` со старым
  полем `resourceProduction`. Осознанное отклонение, задокументировано в
  commit message Среза 1.
- **Точность миграции превышает критерий приёмки**: критерий требовал
  «суммарный output равен прежнему ±1%» — фактически достигнуто точное
  (0% дрейфа) совпадение: `deposits = resourceProduction`,
  `extraction = MAX_EXTRACTION_LEVEL` везде → `extractionFactor = 1.0`
  побайтово воспроизводит старый output. Проверено скриптом
  сравнения JSON до/после прогона `fill_region_economy_1946.py`.
- **Шаг 6 плана (связь с MapFeature, план 06) не реализован** — явно
  вынесен в «За скобками» (переименован в «Явно не в этом заходе» при
  планировании): `buildExtraction` меняет только `Region.extraction`,
  визуальная фича `mine` на карте не создаётся. Требует плана 06
  (`client/src/map/**`, вне периметра этого захода — карта заморожена).
- **`techGate?` на депозите** (упомянут в целевой модели плана) не введён —
  `RESOURCE_CATALOG` уже даёт `eraIntroduced`/`techGate` на уровне ресурса,
  этого достаточно сегодняшним критериям.
- **Побочный фикс `GeminiProvider.ts`**: добавление `delta: z.union([z.literal(1),
  z.literal(-1)])` в Zod-схему `build_extraction` обнажило баг в
  `mergeIdenticalShapeBranches`/`enrichForGemini` (Срез 4 плана 02) — эти
  функции были написаны только под дискриминированный union объектов и
  падали (`TypeError`) на вложенном `anyOf` из литералов-не-объектов.
  Исправлено guard-функцией `isMergeableDiscriminatedBranch`; `const→enum`
  конверсия заодно обобщена с «только string» на любой тип значения. Не
  относится к ресурсам по существу, но было необходимо для прохождения
  тестов Среза 4 — задокументировано здесь, а не в файле плана 02, так как
  обнаружено и исправлено в рамках этой работы.
- **Автоматический триггер `damageExtraction` от войны/событий** — как и
  планировалось, не подключён; команда существует и тестируется напрямую.
