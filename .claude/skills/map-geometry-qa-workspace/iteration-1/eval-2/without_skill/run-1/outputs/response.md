# Зазор Iraq / Kirkuk на карте 1946 — как закрыть

## Коротко

Закрывать нужно тем же способом, который этот проект уже использует для
всех похожих швов после разбиения региона — **gap-first `absorb_slivers`**
(`scripts/map/build/geometry_cleanup.py`), вызванный из
`build_asia_1946.py` тем же паттерном, что уже есть для шва Палестина/
Иордания/Сирия/Ливан. **Не `buffer()`** — этот подход в проекте уже
пробовали как основной метод дозаполнения зазоров, он трижды ломался в
реальной работе над этой картой и был осознанно и полностью выпилен
(`docs/DECISIONS.md`, запись `2026-07-19-e`).

Ниже — почему, как это устроено в реальном коде репозитория, конкретный
план правки и то, что я обнаружил, когда попробовал сам эмпирически
проверить, есть ли зазор прямо сейчас.

## Важная оговорка о ветках

Разбиение Kirkuk (коммит `d8236d7`, "carve Kirkuk out of Iraq") живёт на
ветке `claude/1946-map-geometry-cleanup` (сейчас выписана в отдельный
worktree, независимый от того, где выполняется эта задача), которая ещё
**не влита в `main`**. Тот worktree, где я разбирал этот вопрос, ответвлён
от `main` и Kirkuk не содержит вообще: `scripts/map/build/
geometry_cleanup.py` там просто не существует, поиск `kirkuk` по
`scripts/map/`+`server/data/scenarios/1946/` даёт 0 совпадений. Весь
разбор ниже — по чтению кода и истории решений НА ТОЙ ветке (через прямое
чтение файлов её worktree и через `git show <SHA>:<path>`, без
переключения/правки), не по файлам, которые лежат в рабочем дереве этой
задачи. Практическое следствие: сам фикс имеет смысл вносить именно на
той ветке (или после её мержа в `main`).

## Почему не buffer()

Buffer-подход (наращивание полигонов навстречу друг другу через
`.buffer(eps)`) уже был основным методом дозаполнения на этой самой карте
и был полностью заменён 19 июля (коммит `af0ca49`, "replace buffer-based
gap-filling with gap-first absorb_slivers") по прямому требованию
пользователя — в `docs/DECISIONS.md` сохранена цитата: «Пока не будет
идеального "прилипания" полигонов — не отстану. Надо разработать надёжный
алгоритм». У buffer три задокументированных врождённых дефекта, и каждый
уже успел стать реальным багом на этой карте, не гипотезой:

1. **Форма шва зависит от `join_style`.** Круглый (дефолтный) join на
   выпуклом угле рисует дугу вместо прямой линии — видимая "пипка" (баг
   был найден на Газе). Buffer *придумывает* новую геометрию вместо того,
   чтобы привязаться к уже существующей границе соседа.
2. **Пороговый радиус подбирается руками под конкретный стык** — это не
   общий переиспользуемый алгоритм, а параметр, который надо заново
   подбирать под каждый новый шов.
3. **Buffer раздувает полигон во все стороны, не только к нужному
   соседу**, и сходимость за один проход не гарантирована. В реальном
   инциденте на этой карте дозаполнение Иордании к соседям попутно
   наложило её на Ирак и Сирию, а Беэр-Шеву — на залив Акаба (в
   `scripts/map/README.md` он назван транслитерацией «Гулф-оф-Акаба»),
   что потребовало каскада дополнительных клипов только чтобы вернуть то,
   что buffer сам же случайно испортил.

Для пары Iraq/Kirkuk это не абстрактный риск: если зазор закрывать
буфером именно Kirkuk (или именно "иракского" кластера), есть реальный
шанс наехать на настоящих соседей Ирака (Иран, Турция, Сирия, Кувейт,
Саудовская Аравия) или на воду Персидского залива — то есть создать
новые наложения там, где раньше всё было в порядке. Это ровно тот класс
регрессии, который buffer уже устраивал на этой же карте.

## Как устроен gap-first (`absorb_slivers`)

Метод в `scripts/map/build/geometry_cleanup.py` (там же полный докстринг
с обоснованием):

1. `polygonize()` (построение мозаики непересекающихся ячеек из набора
   линий) объединения ВСЕХ границ — изменяемая земля + земля соседей +
   вода — даёт точную мозаику ячеек плоскости, без допущений о форме.
2. Ячейка, чья `representative_point()` не покрыта ни землёй, ни водой —
   это и есть настоящий зазор: не наращённая догадка, а буквально пустая
   ячейка на стыке уже существующих полигонов.
3. Каждая такая ячейка ("sliver") отдаётся той изменяемой фиче, с которой
   у неё самая длинная общая граница; длинные вытянутые ленты режутся
   пополам рекурсивно, чтобы разные участки длинного зазора доставались
   разным ближайшим регионам, а не один "победитель" забирал всю ленту.

По построению: новых наложений быть не может (ячейка — пустота, ни с кем
не пересекается), один проход сходится (`absorb_slivers_until_stable`
гоняет второй проход только как проверку инварианта — он должен поглотить
0 ячеек), шов проходит ровно по уже существующей границе соседа — то
самое идеальное "прилипание", которое требовал пользователь в решении
`2026-07-19-e`.

У функции есть встроенные защиты, которые важно не сломать при
распространении на новую пару регионов: порог площади для компактных
"блобов" (чтобы не проглотить настоящее озеро-дыру), список защищённых
точек для уже известных озёр, исключение для вытянутых лент, отбрасывание
ячеек, обрезанных рамкой bbox.

## Как именно вырезан Kirkuk (реальный код `build_asia_1946.py`)

Kirkuk — не "фича без источника" (как, скажем, Байконур или Кашмир через
`EXTRA_SINGLE_FEATURES` по `adm1_code`), а результат `ZONED_GEOMETRIC["IQ"]`:

```python
ZONED_GEOMETRIC = {
    "IQ": {
        "field": "region",
        "targets": {"Iraq": 6, "Kurdistan": 3, "Kirkuk": 1},
    },
}
```

плюс отдельный проход ДО `geometric_merge_by_zone`, который находит
сырую провинцию, переименованную `NAME_OVERRIDES_1946` из `At-Ta'mim`
(бюрократическое название с 1976 года) в `"Kirkuk"`, и помечает её
`region_field = "Kirkuk"` — то есть выделяет в зону-синглтон раньше, чем
остальные провинции Ирака уйдут в зоны `"Iraq"` (6 шт.) и `"Kurdistan"`
(3 шт., это и есть реальные губернаторства Иракского Курдистана — Dihok/
Arbil/As-Sulaymaniyah).

`geometric_merge_by_zone` группирует сырые провинции по `region_field` и
на каждую группу отдельно вызывает `reduce_clusters(group, target)`.
Именно здесь и может появиться шов: если `reduce_clusters` реально
сливает (`unary_union`) несколько сырых провинций внутри зоны, стык между
результатом одной зоны и результатом другой зоны не гарантированно
останется побитово идентичным исходной границе — тот же класс проблемы
плавающей точки, что уже документирован в `geometry_cleanup.py` для
Палестины/Голана.

## Куда конкретно добавить вызов

В `build_asia_1946.py` уже есть точный прецедент — `absorb_middle_east_
slivers(features)`, вызываемый из `main()`:

```python
MUTABLE_ISO = {"PS", "JO", "SY", "LB"}
...
absorb_slivers_until_stable(mutable, context, water, clip_box, label="MidEast")
```

**Важно: Ирак (и, соответственно, Kirkuk) сюда не входит** — Iraq в этом
вызове используется только как `context` (авторитетный сосед, по
которому чинят Палестину/Иорданию/Сирию/Ливан, сам не двигается). То есть
готового шага, который искал бы зазор МЕЖДУ иракскими кластерами
(включая Kirkuk), в пайплайне сейчас нет — если такой зазор
подтвердится, для него нужен отдельный вызов того же движка, а не
расширение существующего `absorb_middle_east_slivers`.

Рекомендуемая форма — по месту вызова как у `absorb_middle_east_slivers`,
а по размеру `mutable`-набора как у `fix_china_geometry.py` (там весь
набор кластеров ОДНОЙ страны идёт одним mutable-списком):

```python
def absorb_iraq_zone_slivers(features):
    """Слайверы внутри ZONED_GEOMETRIC["IQ"]: Kirkuk против Kurdistan/Iraq
    кластеров (и друг против друга), плюс шов с реальными соседями Ирака."""
    mutable = [ft for ft in features if ft["properties"]["iso_a2"] == "IQ"]
    if not mutable:
        return
    minx, miny, maxx, maxy = unary_union(
        [shape(ft["geometry"]) for ft in mutable]).bounds
    clip_box = shp_box(minx - 0.5, miny - 0.5, maxx + 0.5, maxy + 0.5)
    context = [shape(ft["geometry"]).intersection(clip_box)
               for ft in features
               if ft["properties"]["iso_a2"] != "IQ"
               and shape(ft["geometry"]).intersects(clip_box)]
    water = load_water_geoms(clip_box)
    absorb_slivers_until_stable(mutable, context, water, clip_box, label="IQ-zone")
```

вызвать в `main()` сразу после существующего вызова:

```python
absorb_middle_east_slivers(out_features)
absorb_iraq_zone_slivers(out_features)   # новая строка
```

(это иллюстрация подхода, а не патч, который я применил — см. ниже, почему
я не стал его коммитить.) Порядок важен так же, как уже описано в
`scripts/map/README.md` на той ветке: сначала клипы наложений, потом
absorb — новый вызов логично ставить после `absorb_middle_east_slivers`,
а не до.

Не берите за образец `fix_china_geometry.py` целиком как способ запуска —
этот скрипт патчит уже закоммиченный `china_1946_historical.json`
отдельным постпроцессингом, потому что китайский источник давно
невоспроизводим и `build_china_1946_v2.py` его не пересобирает. Ирак —
не такой случай: `build_asia_1946.py` полностью воспроизводим, значит
фикс обязан жить ВНУТРИ `main()`, а не отдельным разовым скриптом —
иначе он тихо потеряется при следующей пересборке континента.

## Что я реально проверил (и что это значит)

Поскольку в моём рабочем дереве Kirkuk не существует, я вытащил
`client/public/world_1946.geojson` с ветки `claude/1946-map-geometry-cleanup`
через `git show <SHA>:<path>` (без переключения на неё) и прогнал по нему
две проверки:

1. **Числовая.** `shapely` `distance()`/`touches()` между `Kirkuk` и
   каждым из 9 остальных иракских выходных регионов: с тремя его
   реальными соседями (`Arbil`, `As-Sulaymaniyah`, `Sala ad-Din`) —
   `touches=True`, `overlap_area=0.0`; с остальными Kirkuk вообще не
   граничит (0.17° и больше). Локальный `polygonize` вокруг Kirkuk
   (bbox + 0.3°) — 0 непокрытых ячеек.
2. **Рендер** (matplotlib, по принятой в этом проекте практике — отдельный
   скрипт, зум на конкретный регион и его реальных соседей, `Path`/
   `PathPatch` по exterior и interiors, а не голый `ax.fill`, который
   прячет настоящие дыры) — общий вид и точечные зумы до ~0.02°
   (~1-2 км) вдоль реальных общих границ с Arbil и с Sala ad-Din:
   везде один чистый общий контур, без шва и без нахлёста.

**Вывод: в текущем закоммиченном состоянии этой ветки видимого зазора
между Kirkuk и его иракскими соседями нет.** Похоже, это не случайность:
`reduce_clusters()` при `len(clusters) <= target` возвращает кластеры без
единого `unary_union` — а у зоны `Kirkuk` (1 сырая провинция, target=1)
и, судя по тому, что все 9 остальных иракских выходных регионов остались
отдельными, узнаваемыми по имени провинциями (а не слитыми
многоимёнными кластерами), похоже, и у `Kurdistan` (3 сырые провинции,
target=3), и у `Iraq` (6 сырых провинций, target=6) это условие
выполняется буквально — ни один из 10 итоговых иракских регионов сейчас
не является склейкой нескольких сырых провинций, каждый нетронут с
исходного источника, и взяться новому шву плавающей точки неоткуда. Это
согласуется и с `.agent/plans/west-bank-governorates-kirkuk-split.md` —
в исходной сессии, вырезавшей Kirkuk, рендер Iraq/Kirkuk уже проверялся
и был отмечен как чистый.

**Это не значит, что вопрос неактуален:**

- Если зазор виден в чьём-то реальном рендере — это либо более свежее
  локальное состояние (например, точечная правка границы Kirkuk из
  исторических соображений `docs/HISTORICAL_ACCURACY.md`), либо
  артефакт тоньше, чем я проверил здесь (я смотрел до ~1-2 км, а не до
  метра). Оба варианта — ровно тот класс проблемы, для которого
  `absorb_slivers` и написан.
- История этого репозитория (расширенный чек-лист в `scripts/map/
  README.md` на той ветке) — это по сути каталог случаев "числовая
  проверка прошла чисто, а зазор всё равно был виден только на
  зумированном рендере" (Газа/Беэр-Шева, побережье Ливана, кольца вокруг
  Great Lakes и другие). Поэтому я не стал бы утверждать "зазора нет"
  только по своей проверке — если работа над этим продолжится, первый шаг
  должен быть ПОДТВЕРДИТЬ конкретный зазор существующим read-only
  диагностическим инструментом или точечным рендером, а не считать его
  данностью по одной формулировке задачи.

## Как проверять результат (обязательно рендером, не только числом)

Правило, закреплённое в этом проекте по итогам нескольких реальных
инцидентов: числовые проверки (invalid/overlaps/`distance()`) — это
фильтр ДО рендера, а не замена ему; `touches()`/`distance()==0` не
гарантируют настоящего касания после любой операции с геометрией.
Конкретно для Iraq/Kirkuk:

1. Прогнать `scripts/map/build/diagnose_coastline_gaps.py --render
   <bbox Kirkuk>` — этот read-only инструмент уже существует на той
   ветке специально для подобной проверки: ничего не пишет, классифицирует
   кандидатные ячейки на "касается воды" / "вероятная настоящая дыра" /
   "шум несовпадающих административных границ", чтобы не спутать реальный
   зазор с обычной зубчатостью соседних контуров.
2. Дополнительно — точечный matplotlib-рендер конкретно Kirkuk +
   Arbil/As-Sulaymaniyah/Sala ad-Din/Diyala (его реальные соседи) с
   несколькими зумами вдоль общей границы, не только общий вид региона.
3. Закрытым шов считать только после чистого рендера — а не только
   потому что `absorb_slivers` напечатал "поглощено слайверов: 0".

## TL;DR

- Метод: **gap-first `absorb_slivers`/`geometry_cleanup.py`**, вызванный
  из `build_asia_1946.py::main()` тем же паттерном, что уже есть для
  Ближнего Востока (`absorb_middle_east_slivers`) — новая функция с
  `mutable = все iso_a2=="IQ"`.
- Не `buffer()` — задокументированно заменён в этом же проекте 19 июля
  (`docs/DECISIONS.md`, `2026-07-19-e`) из-за артефактов `join_style`,
  ручной подгонки радиуса под каждый шов и раздувания во все стороны с
  новыми наложениями на третьих соседей — всё это уже реально случалось
  на этой карте, не гипотеза.
- Реальный код разбиения Kirkuk — `ZONED_GEOMETRIC["IQ"]` в
  `build_asia_1946.py` на ветке `claude/1946-map-geometry-cleanup`; в
  worktree, где выполнялась эта задача, этого кода ещё нет (ветка не
  влита в `main`).
- Я проверил сам: на текущем коммите той ветки видимого зазора между
  Kirkuk и его соседями нет ни числом, ни рендером (до ~1-2 км). Прежде
  чем писать код фикса — стоит заново подтвердить зазор рендером или
  `diagnose_coastline_gaps.py`, а не считать его данностью.
- Проверка результата — обязательно рендером до/после, не только по
  счётчику поглощённых ячеек.
