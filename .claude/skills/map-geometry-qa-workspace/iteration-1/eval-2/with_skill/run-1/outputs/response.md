# Зазор Iraq ↔ Kirkuk: как закрывать

## Рекомендация коротко

Закрывать **gap-first методом** — `absorb_slivers_until_stable` из
`scripts/map/build/geometry_cleanup.py`, тем же способом, что уже используется
для соседних швов Ближнего Востока (Palestine/Jordan/Syria/Lebanon). **Не
buffer()**. Это не общая теоретическая рекомендация — она следует из того, как
именно Kirkuk вырезан из Iraq в коде, и это тот самый класс задачи, ради
которого в этом репозитории buffer-подход был опробован и явно выброшен
19 июля (запись `2026-07-19-e` в `docs/DECISIONS.md`).

Ниже — на чём это основано, что я реально проверил на текущих данных, и
конкретный код для фикса.

## Как Kirkuk был вырезан на самом деле

Коммит `d8236d7` ("carve Kirkuk out of Iraq") правит только
`scripts/map/build/build_asia_1946.py`. Механизм — не перерисовка границ, а
**переброс сырой провинции между "корзинами" ДО геометрического слияния**:

```python
ZONED_GEOMETRIC = {
    "IQ": {
        "field": "region",
        "targets": {"Iraq": 6, "Kurdistan": 3, "Kirkuk": 1},  # было {"Iraq": 7, "Kurdistan": 3}
    },
}
...
for it in by_country.get("IQ", []):
    if it["name"] == "Kirkuk":       # NAME_OVERRIDES_1946 переименовал At-Ta'mim
        it["region_field"] = "Kirkuk"
        break
```

То есть: сырая провинция At-Ta'mim (переименована в "Kirkuk" — At-Ta'mim это
баасистское название 1976 года, на 1946 год историческое имя именно Kirkuk)
просто помечается как своя зона с целевым числом кластеров = 1 (то есть без
слияния — остаётся как есть) и больше не попадает в пул из 7 провинций,
которые `geometric_merge_by_zone` объединяет в 6 кластеров "Iraq". **Ни сама
провинция Kirkuk, ни её соседи при этом не перерисовываются, не клипаются и не
объединяются заново** — единственная операция это смена ярлыка `region_field`
до `geometric_merge_by_zone`. Никакого нового источника данных, никакого
`buffer()`, никакого `.difference()` в этом месте нет.

Это важно для выбора метода: если бы Kirkuk добавлялся из ДРУГОГО источника
(как Golan/HaZafon или PSE-губернаторства Западного берега в том же коммите),
шов почти гарантированно возник бы от несовпадения независимых оцифровок — и
там в том же коммите пришлось отдельно клипать и склеивать MultiPolygon-обрезки
(HaZafon минус Golan, PSE-Jerusalem слит с существующим Jerusalem). Но Kirkuk
и все его соседи (Arbil, As-Sulaymaniyah, Sala ad-Din, Ninawa, Diyala) — это
**одни и те же сырые ADM1-провинции из одного файла** (`game_map.json`),
просто раньше расфасованные в кластеры `geometric_merge_by_zone` иначе.

## Почему gap-first, а не buffer — для этого конкретного шва

Даже если зазор окажется реальным (пункт 1 выше), это ровно тот случай, для
которого gap-first создавался, а не пограничный случай, где buffer был бы
хоть немного оправдан:

- **Обе стороны — уже существующие, полные, доверенные полигоны одного
  источника** (то же самое `game_map.json`, тот же `build_asia_1946.py`).
  Это НЕ межконтинентальный шов (Asia строится одним проходом, Kirkuk и его
  соседи обрабатываются в одном вызове `main()`) — значит не нужен
  отдельный пост-шаг вроде `fill_palestine_egypt_gap.py`, чинить можно и нужно
  прямо в `build_asia_1946.py`.
- **Суша с двух сторон, воды нет** (Kirkuk — не прибрежный регион) — самый
  простой случай для `absorb_slivers`: `water_geoms` пустой, не нужно думать
  про "1 суша + вода" edge case, каждая пустая ячейка касается 2+ земельных
  фич, и решает правило "самая длинная общая граница".
- **buffer() здесь физически может навредить**: у Kirkuk четыре соседа
  (Kurdistan/Arbil, Kurdistan/As-Sulaymaniyah, Iraq/Sala ad-Din, и рядом
  Ninawa/Diyala) сходятся в паре tripoints за пару километров друг от друга.
  `LineString(...).buffer(r, cap_style=2, join_style=2)` раздувается ВО ВСЕ
  стороны — на таком плотном стыке заметно вырастает риск задеть третьего
  соседа и создать новое наложение, которое потом чистить отдельным клипом
  (в проекте это уже было — Иордания наехала на Iraq/Syria именно так,
  `docs/DECISIONS.md 2026-07-19-e`). Gap-first этой проблемы не имеет по
  построению: слайвер — пустота, она ни с кем не пересекается, наложений
  просто неоткуда взяться.
- **Радиус buffer пришлось бы подбирать руками под этот конкретный стык** —
  gap-first не имеет свободного параметра "насколько раздуть", он берёт
  ровно фактическую пустоту.

## Конкретный код фикса

В `build_asia_1946.py` уже есть готовый шаблон для точно такой же операции —
`absorb_middle_east_slivers()` (строка ~333), которая делает mutable
Palestine/Jordan/Syria/Lebanon, а Iraq держит как context ("авторитетный сосед,
который не двигается" — Iraq назван в скилле `map-geometry-qa` буквально этим
же словом). Естественный фикс — аналогичная функция для внутреннего шва самого
Iraq, вызванная сразу после неё:

```python
def absorb_iraq_internal_slivers(features):
    """Gap-first фикс шва Kirkuk<->Iraq/Kurdistan, если он появится после
    ZONED_GEOMETRIC-переброса Kirkuk в свою зону (2026-07-19-j). Аналог
    absorb_middle_east_slivers, тот же geometry_cleanup.absorb_slivers_
    until_stable. Kirkuk landlocked, water_geoms будет пустым для этого
    clip_box - это не проблема, absorb_slivers работает и без воды."""
    mutable = [ft for ft in features
               if ft["properties"]["iso_a2"] == "IQ" and ft["properties"]["name"] == "Kirkuk"]
    if not mutable:
        return
    minx, miny, maxx, maxy = unary_union([shape(ft["geometry"]) for ft in mutable]).bounds
    clip_box = shp_box(minx - 0.5, miny - 0.5, maxx + 0.5, maxy + 0.5)
    context = []
    for ft in features:
        if ft["properties"]["name"] == "Kirkuk":
            continue
        g = shape(ft["geometry"])
        if g.intersects(clip_box):
            context.append(g.intersection(clip_box))
    water = load_water_geoms(clip_box)
    absorb_slivers_until_stable(mutable, context, water, clip_box, label="Kirkuk-Iraq")
```

и в `main()`, сразу после существующего вызова (строка ~1025):

```python
absorb_middle_east_slivers(out_features)
absorb_iraq_internal_slivers(out_features)   # новая строка
```

`mutable` — только Kirkuk (не его соседи): это самый узкий, самый безопасный
diff, и Kirkuk — единственная фактически "новая" фича на этом стыке, логично
именно ей отдавать спорные ячейки. Если после рендера окажется, что часть шва
явно ближе к соседу, чем к Kirkuk (длинная лента, где один конец логичнее
отдать Ninawa) — тогда по прецеденту `absorb_middle_east_slivers` расширяете
`mutable` до списка из нескольких имён, и правило "самая длинная граница"
само разрежет ленту по сегментам между несколькими получателями.

Смена `region_id`/числа регионов Iraq этим фиксом не происходит (Kirkuk уже
существует, просто меняется его геометрия) — значит `remap_region_ids.py`
после этого **не нужен**, и позиционные файлы (`ownership_1946.json`,
`names_ru.json`) можно не трогать.

## Как проверять после фикса

Стандартный рецепт скилла `map-geometry-qa`, суженный под то, что реально
меняется (только геометрия Kirkuk, без сдвига id):

1. Пересобрать `build_asia_1946.py` (не весь `--full-rebuild`, если остальной
   мир не менялся).
2. Численно: `Kirkuk.buffer(0.01) ∩ neighbor.buffer(0.01) − Kirkuk − neighbor`
   для каждого из 3 касающихся соседей — должно быть ~0; `Kirkuk ∩ neighbor`
   (наложение) — должно остаться 0.
3. **Рендер обязателен, не пропускать** — тот самый пункт скилла "numeric
   checks are a filter, never a substitute for looking": даже у
   `absorb_slivers` в этом репо уже был баг, где численно "сошлось", а
   реальный зазор остался (Great Lakes, коммит `f59b754`, сегодняшний).
   Рендерить именно Kirkuk + Arbil/As-Sulaymaniyah/Sala ad-Din/Ninawa/Diyala,
   не весь мир — деталь пропадает.
4. Гейты: `test_country_entities_1946.py`, `validate_region_economy_1946.py`
   (ожидаем тот же список известных `capitalRegionId`-расхождений, не новый),
   `tsc --noEmit` (client+server), `server` vitest.
5. Живая проверка `/game/start` с проверкой PID на порту (в этом репо уже
   дважды ловили "зомби"-сервер со старыми данными на том же порту).
