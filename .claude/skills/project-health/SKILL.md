# Периодический аудит здоровья проекта

## Trigger

Public eval краснеет с `audit fresh: <область>` — срок жизни аудита истёк.
Либо пользователь просит проверить область прямо. Либо начинается крупная
работа в области, которую давно не смотрели.

## Do not trigger

- Аудит конкретного изменения перед коммитом — это `verify-change`.
- Ревью чужого diff — это роль независимого рецензента, у неё другой вход.
- «Найди все проблемы» без области: без гипотезы агент возвращает общие слова.
  Гипотезы берутся из реестра, а не изобретаются на ходу.

## Required inputs

1. **Область** — `id` из `.agent/audits/registry.json`, обычно самая просроченная.
2. **Гипотезы этой области** — оттуда же, поле `hypotheses`. Это список того,
   что уже ломалось; он важнее фантазии проверяющего.
3. **Предыдущий отчёт** (`report`) — чтобы отличить новую находку от известной.
4. **Живые данные**, а не фикстуры: сценарий `server/data/scenarios/1946/`.

## Workflow

### Почему именно так

Аудит 2026-07-30 нашёл шесть дефектов, невидимых 1276 зелёным тестам, потому что
проверял формулы **на распределении реального мира**, а не на подобранном
примере. Ни одна находка не была бы получена чтением кода без данных: «порог
−70 при достижимом минимуме −20» и «равновесие 70 у 154 стран из 157» — это
арифметика по живому сценарию, а не впечатление.

### Шаги

1. **Взять область и её гипотезы** из реестра. Не расширять: одна область за
   проход, иначе отчёт превращается в обзор.
2. **Установить факты по коду**, а не по комментариям и докам. Расхождение
   комментария с кодом — находка сама по себе («утверждение сильнее гарантии» —
   зафиксированный класс дефекта проекта).
3. **Посчитать на живых данных.** Для каждой гипотезы — конкретное число:
   сколько стран получают одинаковое значение, какой фактический диапазон входа,
   сколько регионов пересекают порог. Утверждение без числа — не находка.
4. **Отделить симптом от класса.** Три места с одной и той же путаницей шкал —
   это один дефект, а не три; чинить надо конвенцию, а не вхождения.
5. **Проверить обратное:** назвать и то, что подтвердилось РАБОТАЮЩИМ. Иначе
   следующая сессия перепроверит то же самое.
6. **Оценить, чинится ли находка правилом или проверкой.** Правило в тексте —
   слабейшая форма: правило чистки журнала существовало три недели и не
   выполнилось ни разу. Если находку можно поймать машиной — предложить строку
   в eval, а не абзац в своде (там всё равно нет места).

### Делегирование

Область шире одной подсистемы — разбить на непересекающиеся части и запустить
параллельных read-only субагентов с ЕДИНОЙ рамкой оценки: без общей рамки
отчёты не сводятся. Каждому давать список гипотез и требовать вердикт из
фиксированного набора (подходит / шатко / дефект) плюс приоритет.

## Verification and failure conditions

1. Код не изменён: аудит read-only, `git status` в конце чист.
2. Каждая находка несёт **файл:строку и число**, а не оценку.
3. Проверено, что находка не описана в предыдущем отчёте области.
4. Прогнан public eval — он мог поймать что-то из того же класса.
5. **Провалом считается отчёт без чисел** и отчёт, в котором не названо ничего
   работающего: первое означает, что аудит не прогонялся на данных, второе — что
   проверяющий искал только подтверждение своих ожиданий.

## Output

- Отчёт `.agent/audits/<область>-<дата>.md`: сводная таблица (формула/место/
  вердикт/приоритет), развёрнуто по каждому дефекту, отдельно подтверждённое
  работающим, отдельно — что осталось непроверенным.
- Живые задачи — в `docs/TODO.md` кратко, со ссылкой на отчёт за деталями.
- Идеи вне scope — в `docs/IDEAS.md`.
- **Обновить `.agent/audits/registry.json`**: `lastAudited`, `report`, и — если
  нашлись новые классы — дополнить `hypotheses`. Без этого eval продолжит
  краснеть, и следующая сессия будет искать по старому списку.
