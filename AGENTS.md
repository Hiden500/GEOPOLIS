# Geopolis — правила работы агента

Язык ответов по умолчанию — русский. Код, идентификаторы, команды и ошибки
оставляй в оригинале.

Пользователь — начинающий программист: учится разработке игр и работе с
AI-инструментами. Нетривиальные технические шаги объясняй по ходу дела — что
делаешь, зачем, что это меняет — коротко и без снисходительности; незнакомый
термин раскрывай одной фразой при первом употреблении. Это не повод спрашивать
подтверждение на обратимые технические решения — решай сам и объясняй; выбор
пользователя нужен для продуктовых и необратимых развилок. Идеи пользователя
оценивай профессионально и возражай с альтернативами, когда идея слаба, — не
поддакивай.

## Миссия и границы

Geopolis — локальная геополитическая grand strategy: дипломатия, война,
экономика, политика, альтернативная история и мировая симуляция без лишнего
микроменеджмента. Проект рассчитан на тысячи регионов и долгие кампании:
избегай полных обходов мира, раздувания save-файлов и отправки полного
состояния в LLM.

Модули и их правила:

- `client/` — React/Vite UI и MapLibre (`client/AGENTS.md`);
- `server/` — API, сервисы, детерминированная симуляция (`server/AGENTS.md`);
- `shared/` — общие plain-data типы (`shared/AGENTS.md`);
- `scripts/map/` — генерация и проверка сценарных данных
  (`scripts/map/AGENTS.md`).

Работаешь в нескольких модулях — прочитай каждый применимый nested `AGENTS.md`.
Новые instruction-файлы не создавай без устойчиво отличающихся команд или
ограничений.

## Источники истины

Код и исполняемая конфигурация описывают текущее поведение; профильные docs —
намерение и ограничения. `docs/TODO.md` — только живой backlog,
`docs/DECISIONS.md` — последние решения и индекс открытых вопросов,
`docs/decisions/` и завершённые планы — история. У обоих живых файлов порог
размера в public eval: упёрся — переноси в архив месяца, не поднимай порог. Два слоя планов не смешивай:
`docs/plans/` — продуктовые планы систем игры, `.agent/plans/` — ExecPlan'ы
конкретных задач агентов.

Перед нетривиальной работой: проверь `git status`, ветку и последние коммиты
(автоматический `checkout`, `pull`, очистку worktree не делай); прочитай
относящиеся к задаче разделы `TODO`/последних решений, не журнал целиком, затем
профильный документ и реализацию. Для индексированных файлов — Repowise, если
доступен, иначе `rg` и точечные чтения.

| Область | Канонический документ (пути от `docs/`) |
|---|---|
| Ядро игры, алфавит примитивов | `CONCEPT.md`, `PRIMITIVES.md` |
| Архитектура | `ARCHITECTURE.md`, `PROJECT.md` |
| Порядок тиков/AI, LLM | `AI_RULES.md`, `LLM_RULES.md` |
| Экономика, политика, война, торговля, дипломатия | `ECONOMY.md`, `POLITICS.md`, `WAR.md`, `TRADE.md`, `DIPLOMACY.md` |
| Локализация, UI | `LOCALIZATION.md`, `UI_DESIGN.md` |
| Карта, данные, сценарии | `MAP_FEATURES.md`, `SCENARIOS.md`, `HISTORICAL_ACCURACY.md` |
| Мир, tech, events | `WORLD.md`, `TECH_TREE.md`, `EVENTS.md` |
| Цели игрока | `OBJECTIVES.md` |

`docs/provenance/` — происхождение данных, `docs/agent/` — исторический
bootstrap (SUPERSEDED), `docs/IDEAS.md` — предложения; всё это не нормативно.

Нахождение в `docs/` само по себе не делает документ instruction authority.
Расходится живой нормативный документ с кодом — зафиксируй конфликт явно. В
обычной feature-задаче продуктовую семантику без решения пользователя не меняй;
в явно заказанном аудите/синхронизации исправляй подтверждённый drift по коду и
истории решений.

## Worktree и параллельная работа

Над репозиторием параллельно работают несколько агентов (Claude, Gemini,
Antigravity). Изоляция и координация:

- Задача, изменяющая файлы, идёт в отдельном linked worktree на своей ветке
  (`claude/<task>`, `gemini/<task>`, `antigravity/<task>`): один изменяющий
  агент = одно дерево = одна ветка = одна задача. Уже в корректном дереве своей
  задачи — используй его, вложенный не создавай.
- **Основной checkout (`D:/Pax Historia LOCAL`) не редактируй и не переключай:**
  он может быть занят чужой живой сессией. Ветку другого агента не мержи, не
  ребейзь и не удаляй; интеграцию в `main` инициирует пользователь. Влитие
  чужой ветки — отдельная задача, скилл `integrate-branch`.
- Дерево живёт ровно столько, сколько его задача: заводи через
  `scripts/worktree-new.ps1`, после вливания ветки убирай через
  `scripts/worktree-drop.ps1` — он отказывает на незакоммиченных изменениях и
  невлитой ветке. **Ручной `git worktree remove --force` мимо этих проверок —
  способ стереть чужую живую работу.**
- Перед стартом смотри `git worktree list`, `git branch -a` и активные
  `.agent/plans/*.md`. Пересечение области с параллельной задачей назови до
  реализации, не после: дерево изолирует файлы, но не смысл — два агента могут
  принять несовместимые решения. При риске пересечения область («что меняю /
  что не трогаю / с чем могу конфликтовать») фиксируется в ExecPlan.
- Роли — функции, не модели: ведущий (требования), исполнитель (реализует в
  своём дереве), независимый рецензент (проверяет требования и diff, не
  принимая объяснения автора за доказательство), аудитор системы
  (`.agent/EVOLUTION.md`). Малая обратимая задача совмещает первых двух,
  независимое ревью обязательно при повышенном риске.

## Инженерные правила

- Сначала установи фактическое состояние, затем меняй минимальный полный scope.
- **Защищай объём v1.** Пользователь склонен усложнять и просил поправлять
  (2026-07-31). Идея, без которой партия проходится насквозь, — запись в
  `docs/IDEAS.md` с горизонтом «после v1», не работа: скажи это, предложи
  минимальную версию и продолжай.
- Переиспользуй существующие сервисы, типы, schemas и тестовые паттерны.
- Архитектурный rewrite — только по явному согласованию.
- Зависимости и ВНЕШНИЕ ДАННЫЕ — только с доказанной пользой и проверкой
  provenance, сопровождения, лицензии, security cost: датасет проверяется как
  пакет, лицензия бывает не там, где её ищет сканер. Реестр источников —
  `docs/plans/11_MVP_ROADMAP.md`.
- Новые user-facing UI-строки — через `react-i18next`, новые shared names —
  через `LocalizedText` (`docs/LOCALIZATION.md`).
- LLM не рассчитывает экономику, производство, бой и pathfinding и не изменяет
  savegame вне валидируемых команд.
- `shared/src/types/` не редактируй параллельно в нескольких ветках.
- Секреты не раскрывай; `.env` не читай без конкретной диагностики, в отчётах
  называй только ключи и пути.
- Не ослабляй sandbox, approvals, проверки, типизацию и security controls.
- Тест проверяет свойство, а не снимок: не хардкодь id, доли и пороги, которые
  изменит следующее наполнение данных. Фикстура доказывает, что функция считает;
  что вход ЖИВОЙ — только прогон на реальных данных: константа у всех стран и
  недостижимый порог зелёным тестам не видны.
- «Никогда»/«всегда» в комментарии или доке — только вместе с тестом, который
  это держит; утверждение сильнее гарантии — повторяющийся в проекте дефект.

## Планирование и делегирование

ExecPlan обязателен для cross-module features, миграций, крупных рефакторингов,
security-sensitive и длительных работ. Формат и lifecycle — `.agent/PLANS.md`.

`.agent/` — инфраструктура агентной системы, не feature-документация; формат
каждого файла описан в нём самом:

- `PLANS.md` + `plans/` — ExecPlan'ы;
- `EVOLUTION.md` — evidence-gated журнал изменений самой системы (промптов,
  skills, config): durable-правка только по повторяющейся проблеме с evidence,
  не по единичному впечатлению;
- `CHARTER.proposed.md` — предложенный (НЕ утверждённый) charter, не security
  boundary; `audits/`, `runs/` — история, после фиксации append-only;
  `evals/public/run_public_evals.py` — обязательный прогон при любом изменении
  agent-конфигурации.

Субагенты — для независимых read-heavy аудитов, поиска и adversarial review:
узкие непересекающиеся области, без параллельной правки одного файла.
Повторяемые workflows — в `.agents/skills/`.

Пользователь разрешил (2026-07-19) заводить skills, агентов и прочую агентную
инфраструктуру по правилам `EVOLUTION.md`. Перед выводом «решения/данных не
существует» и перед внешней альтернативой обязателен скилл
`find-existing-solutions`.

## Проверка

Реальные команды:

```text
client: npx tsc --noEmit -p tsconfig.app.json
client: npm test
client: npm run lint
client: npm run build
server: npx tsc --noEmit -p tsconfig.json
server: npm test
root:   python scripts/map/validate_region_economy_1946.py
root:   python scripts/map/test_validate_region_economy_1946.py
root:   python .agent/evals/public/run_public_evals.py
```

Выбирай проверки по затронутому scope, начиная с узких; для agent-конфигурации
public eval обязателен. Не называй проверку успешной без запуска и просмотра
результата. Предсуществующий failure отделяй от регрессии, не маскируй и не
расширяй. Полный matrix — скилл `verify-change`.

Повторную верификацию закрытия заменяет негативный контроль автора: новый тест
обязан падать на восстановленном старом поведении, и это показывается в отчёте.
Тест, не проверенный на способность падать, покрытием не считается.

## Git, документация и завершение

- Чужие незакоммиченные изменения сохраняй; destructive Git не используй.
- Локальный commit разрешён после релевантных проверок и просмотра diff. Push,
  merge, force-push, release и deploy требуют отдельного разрешения.
- Меняешь поведение или архитектуру — обнови профильный source of truth в тот
  же turn: завершённое удали из `TODO`, реальные решения и отсрочки внеси
  краткой датированной записью в `DECISIONS`. Read-only аудит сам по себе docs
  не меняет.
- Перед завершением проверь diff, незаконченные placeholders, случайные файлы,
  docs drift и итоговый `git status`.
- После нетривиальной задачи — короткая ретроспектива; durable-правка агентной
  системы только по evidence повторяемой проблемы (`.agent/EVOLUTION.md`).
- Сессия не бесконечна: после закрытой задачи, после сжатия контекста и при
  первом «число названо, но в этой сессии не измерено» — `session-handoff`.
- В отчёте отдели: что изменено и почему; что реально проверено; baseline
  failures; что осталось `UNKNOWN` или требует свежей сессии.
- Идея или риск вне scope — строкой в отчёт и в `docs/IDEAS.md` (там же
  отклонённые). Предлагать ≠ делать: минимальный scope ограничивает действия,
  не наблюдения.
