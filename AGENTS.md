# Geopolis — правила работы агента

Язык ответов по умолчанию — русский. Код, идентификаторы, команды и ошибки
оставляй в оригинале.

## Миссия и границы

Geopolis — локальная геополитическая grand strategy. Изменения должны
поддерживать дипломатию, войну, экономику, политику, альтернативную историю и
мировую симуляцию без лишнего микроменеджмента. Проект рассчитан на тысячи
регионов и долгие кампании: избегай полных обходов мира, раздувания save-файлов
и отправки полного состояния в LLM.

Основные модули:

- `client/` — React/Vite UI и MapLibre; дополнительные правила в
  `client/AGENTS.md`;
- `server/` — API, сервисы и детерминированная симуляция; правила в
  `server/AGENTS.md`;
- `shared/` — общие plain-data типы; правила в `shared/AGENTS.md`;
- `scripts/map/` — генерация и проверка сценарных данных; правила в
  `scripts/map/AGENTS.md`.

При работе сразу в нескольких модулях прочитай каждый применимый nested
`AGENTS.md`. Не создавай новые instruction-файлы без устойчиво отличающихся
команд или ограничений.

## Источники истины

Код и исполняемая конфигурация описывают текущее поведение. Профильные docs
описывают намерение и ограничения. `docs/TODO.md` содержит только живой
backlog, `docs/DECISIONS.md` — последние решения и индекс открытых вопросов,
а `docs/decisions/` и завершённые планы — историю.

Перед нетривиальной работой:

1. Проверь `git status`, текущую ветку и последние коммиты; не делай
   автоматический `checkout`, `pull` или очистку worktree.
2. Прочитай относящиеся к задаче разделы `TODO`/последних решений, не весь
   журнал целиком.
3. Прочитай профильный документ и реализацию. Для индексированных файлов
   используй Repowise, если он доступен; иначе — `rg` и точечные чтения.

Маршрутизация документации:

| Область | Канонический документ |
|---|---|
| Архитектура | `docs/ARCHITECTURE.md`, `docs/PROJECT.md` |
| Порядок тиков/AI | `docs/AI_RULES.md` |
| Экономика/политика | `docs/ECONOMY.md`, `docs/POLITICS.md` |
| Война/торговля/дипломатия | `docs/WAR.md`, `docs/TRADE.md`, `docs/DIPLOMACY.md` |
| LLM | `docs/LLM_RULES.md` |
| Локализация | `docs/LOCALIZATION.md` |
| UI | `docs/UI_DESIGN.md` |
| Карта/данные/сценарии | `docs/MAP_FEATURES.md`, `docs/SCENARIOS.md`, `docs/HISTORICAL_ACCURACY.md` |
| Мир/tech/events | `docs/WORLD.md`, `docs/TECH_TREE.md`, `docs/EVENTS.md` |

Документ не становится instruction authority только из-за нахождения в
`docs/`. Если живой нормативный документ расходится с кодом, явно зафиксируй
конфликт. Для обычной feature-задачи не меняй продуктовую семантику без решения
пользователя; для явно заказанного аудита/синхронизации исправляй подтверждённый
drift по коду и истории решений.

## Инженерные правила

- Сначала установи фактическое состояние, затем меняй минимальный полный scope.
- Переиспользуй существующие сервисы, типы, schemas и тестовые паттерны.
- Не делай архитектурный rewrite без явного согласования.
- Не добавляй зависимости без доказанной пользы и проверки provenance,
  сопровождения, лицензии и security cost.
- Новые user-facing UI-строки сразу проводят через `react-i18next`; новые
  shared names — через `LocalizedText`. Детали в `docs/LOCALIZATION.md`.
- LLM не рассчитывает экономику, производство, бой или pathfinding и не
  изменяет savegame вне валидируемых команд.
- `shared/src/types/` не редактируй параллельно в нескольких ветках.
- Не раскрывай секреты. Не читай значения `.env`, если задача не требует
  конкретной диагностики; в отчётах называй только ключи и пути.
- Не ослабляй sandbox, approvals, проверки, типизацию или security controls.

## Планирование и делегирование

ExecPlan обязателен для cross-module features, миграций, крупных рефакторингов,
security-sensitive и длительных работ. Формат и lifecycle — `.agent/PLANS.md`.

Субагенты полезны для независимых read-heavy аудитов, поиска и adversarial
review. Делегируй узкие непересекающиеся области; не допускай параллельного
редактирования одного файла. Повторяемые workflows лежат в `.agents/skills/`.

## Проверка

Реальные команды:

```text
client: npx tsc --noEmit -p tsconfig.app.json
client: npm test
client: npm run lint
client: npm run build
server: npx tsc --noEmit -p tsconfig.json
server: npm test
root:   python scripts/map/validate_region_economy_1946.py
root:   python scripts/map/test_validate_region_economy_1946.py
root:   python .agent/evals/public/run_public_evals.py
```

Выбирай проверки по затронутому scope, начиная с узких. Для изменения agent-
конфигурации public eval обязателен. Не называй проверку успешной без запуска
и просмотра результата. Предсуществующий failure отделяй от регрессии; не
маскируй его и не расширяй. Полный matrix — skill `verify-change`.

## Git, документация и завершение

- Сохраняй чужие незакоммиченные изменения; не используй destructive Git.
- Локальный commit разрешён после релевантных проверок и просмотра diff.
  Push, merge, force-push, release и deploy требуют отдельного разрешения.
- При изменении поведения/архитектуры обнови профильный source of truth в тот
  же turn. Удали завершённое из `TODO`; реальные решения/отсрочки внеси краткой
  датированной записью в `DECISIONS`; read-only аудит сам по себе docs не меняет.
- Перед завершением проверь diff, незаконченные placeholders, случайные файлы,
  docs drift и итоговый `git status`.
- После нетривиальной задачи сделай короткую ретроспективу; persistent
  улучшение вноси только при evidence повторяемой проблемы по
  `.agent/EVOLUTION.md`, не по единичному впечатлению.
- В отчёте отдели: что изменено и почему; что реально проверено; baseline
  failures; что осталось `UNKNOWN` или требует свежей сессии.
